# Durable encrypted native records

`SessionStore::open(path, Arc<VaultService>)` creates a SQLite native record database under the drive's sessions directory. Message bodies, configuration, complete provider messages/tool metadata, pending arguments, checkpoints and workspace memory use XChaCha20-Poly1305 with random nonces and record identity/version AAD. Only opaque IDs and lifecycle state are plaintext SQL metadata.

A random 256-bit record key is generated once while the existing vault is unlocked, stored there under `native-record-encryption-key` (`NATIVE_RECORD_KEY_SECRET`, a record AiDEX manages and clients must not replace or delete), and resolved through short-lived `process:native-record-store` handles. Handles are revoked per operation. No plaintext config key or long-lived decrypted key cache is used. Locked/missing/damaged vaults make private records unavailable; list/status expose only IDs/status. Authenticated decryption failures never produce an empty or plaintext history.

SQLite transactions commit each encrypted record and its run metadata together. Message command IDs bind to input hashes and return the original run when repeated; changed-input reuse fails. Startup interrupts active runs, and private state reconciles with that metadata after unlock. Native execution owns continuation and never repeats pending effects without fresh user action/planning.

The old process-local `SessionCatalog` remains exported for compatibility. It is separate from the durable native service. Independent cryptographic review and whole-database rollback detection remain release-security concerns, as with the existing vault.

## Artifacts

Native sessions own artifacts (`document`, `code`, `data`, `diagram`, `plan`, `web_page`, `other`): `create_artifact(session_id, run_id, NewArtifact { name, kind, mime, language, bytes })`, `list_artifacts(session_id, offset, limit)` (newest first, 1-100 per page), `artifact(id)`, `read_artifact(id, offset, limit)` (pages of at most 64 KiB), `update_artifact(id, bytes)`, `delete_artifact(id)`, and `set_plan_status(id, status)`. A run id must belong to the session.

- **Storage.** The `artifacts` table is created with `IF NOT EXISTS` on open, so daemons that predate it keep opening the same database and never read it. Only the artifact id, the session id and, for blobs, a content address are plaintext columns; `ArtifactMeta` (name, kind, MIME type, language, size, plaintext SHA-256, encoding, plan status, times) is sealed with AAD `aidex-native-v1:artifact:<id>:<session>`. Artifacts are unavailable while the vault is locked, like session history, and deleting a session deletes its artifacts. Rows left by a session that an older daemon deleted are dropped when the store opens (their blobs are then swept), and an artifact whose session is gone reads as not found.
- **Bytes.** Content is sealed in independently authenticated 64 KiB segments whose AAD binds the artifact id, the plaintext SHA-256, the segment index and the segment count, so a paged read decrypts at most two segments and segments cannot be moved, dropped or mixed across artifacts or revisions. Up to 1 MiB is stored inline in the row; larger content (at most 16 MiB) goes to `<db stem>-artifacts/<sha256 of the sealed file>` beside the database (`private/sessions/native-artifacts/` on a drive). Blob files are synced and renamed into place before their row commits; replaced or deleted blobs are removed after commit, and unreferenced blobs and temporary files are swept when the store opens.
- **Encoding.** Content that is valid UTF-8 reads as `utf8`, and its pages start and end on character boundaries (a page always makes progress); anything else reads as `base64` in the daemon's `artifact.read`.
- **Plans.** A `plan` artifact starts `active` and supersedes the session's previous active plan in the same transaction; `set_plan_status` marks a plan `completed` or `superseded`, or makes it `active` again (superseding the other one). Other kinds have no plan status.
- **Limits and validation.** Names are 1-256 bytes without control characters, MIME types are `type/subtype` (parameters are dropped, lowercased), languages are 1-32 bytes of `[a-z0-9+#._-]`. `NewArtifact` and `ArtifactChunk` print byte counts, never content, in `Debug`.

Artifacts and attachments share the segment crypto and blob code (`src/sealed/`). A domain label (`artifact` or `attachment`) in every AAD keeps the two apart, and each has its own blob directory and its own sweep.

## Attachments

Users send images, PDFs and text files with a message. Bytes reach the store through a chunked upload or from a workspace file the daemon reads through its confined root. The store never reads host paths itself.

- **Upload.** `begin_attachment_upload(NewUpload { session_id, name, size, sha256, mime, source })` returns an `UploadTicket { upload_id, chunk_bytes }`. `append_upload(upload_id, offset, bytes)` must continue at the bytes received so far, and every chunk but the last is exactly `chunk_bytes` (256 KiB). A chunk repeated at an earlier chunk offset with that chunk's length is acknowledged without writing. `commit_upload(upload_id)` verifies the declared size and SHA-256, decides the kind and stores the attachment `staged`. An incomplete upload is refused (`bad_offset`) and stays open; any other commit failure ends it. `abort_upload(upload_id)` and `abort_all_uploads()` need no key.
- **Upload hygiene.** Each chunk is sealed into whole 64 KiB segments as it arrives and written to a temporary file in `<db stem>-attachments/`. An upload keeps no key, no cipher and no plaintext between calls. Every call resolves the key again, so a locked vault (the idle auto-lock included) fails the next chunk with `the vault is locked` and drops the upload with its file. The daemon calls `abort_all_uploads` when it locks the vault. An upload with no chunk for 10 minutes is evicted, with its file, at the start of the next upload call (`set_upload_idle_timeout` changes this). At most 8 uploads and 64 MiB of declared bytes are in flight per daemon.
- **Bytes in memory.** `create_attachment(session_id, NewAttachment { name, mime, source, bytes })` and `create_attachment_from_reader(session_id, name, mime, source, reader, size_hint)` store a `staged` attachment with the same rules. The reader variant reads at most 16 MiB plus one byte, into memory that is zeroed on drop.
- **Kinds.** `sniff_attachment` decides the kind from the bytes, never from the client's MIME type:
  - `image`: PNG, JPEG, GIF or WebP, at most 3,750,000 bytes and 8000 px per side. Width, height and animation are read from the headers; an image whose header cannot be read is refused.
  - `pdf`: starts with `%PDF-`, at most 16 MiB and 100 pages. Pages are counted in the file and inside Flate-compressed object streams, or taken from the page tree's `/Count` when that is larger. The count takes time linear in the file and the inflated bytes (at most 64 MiB in total), so a crafted file cannot stall the daemon; an object stream that declares more than 1,000,000 objects is refused (`unsupported_type`). Encrypted PDFs are refused.
  - `text`: UTF-8 without NUL bytes, at most 1 MiB. The client's MIME type is kept when it names text, else `text/plain`. Private key material is refused (`sensitive_content`).
  - Anything else is `unsupported_type`.
- **Names.** The final path component the client sends, trimmed, 1-255 bytes, without control characters, line or paragraph separators, or Unicode format characters (bidi overrides, zero-width characters). Names are display-only and never used as paths.
- **Limits.** At most 40 staged attachments per conversation (uploads in flight included), 256 MiB of staged plus in-flight bytes per drive, and 20 attachments or 32 MiB per message. Staged attachments older than 24 hours are deleted with their blobs when the store opens and, on a running daemon, by the next `begin_attachment_upload`, `create_attachment` or `list_attachments` at most every 5 minutes (`set_staged_expiry_interval` changes this), so drafts a client lost stop counting against these limits without a restart. The constants are exported (`MAX_*`, `UPLOAD_CHUNK_BYTES`, `ATTACHMENT_PAGE_BYTES`, ...).
- **Refusals.** Errors that carry a reason start with `<reason>: `: `too_large`, `too_many_attachments`, `busy`, `bad_offset`, `hash_mismatch`, `unsupported_type`, `sensitive_content`, `too_many_pages`, `attachment_sent`, `attachment_unavailable`, `invalid_name`, `invalid_attachment`. `AttachmentReason::of` splits them. Error text never contains a name, a path or content. Unknown sessions, attachments and uploads give `... not found`; a locked vault gives `the vault is locked`.
- **Reading.**
  - `attachment(id)`; `list_attachments(session_id, offset, limit)` (staged and sent, newest first, 1-200 per page).
  - `message_attachments(session_id)` (sent attachments by message index, in the order they were sent) and `attachments_for_message(session_id, index)`.
  - `read_attachment(id, offset, limit)`: text pages are at most 128 KiB and end on character boundaries, so even fully escaped JSON stays under the 1 MiB RPC line; other pages are at most 512 KiB (base64 in the daemon).
  - `attachment_bytes(id)`: the whole plaintext, zeroed on drop, for prompts.
  - A list skips a row it cannot read, for example one a newer daemon wrote with a new kind (`AttachmentKind::Unknown`, never sent).
- **Sending.** `RunOptions::attachments` lists staged ids for `begin_with`.
  - A repeated command id with the same arguments returns the original run before anything else is checked.
  - For a new command, the ids must be distinct staged attachments of the session (`attachment_unavailable` otherwise, and for a child run). In the same transaction as the new message they become `sent`, with the command, run, message index and position sealed in their metadata.
  - `staged_attachments(session_id, ids)` applies the same checks without changing anything and returns the metadata in order, so the harness can gate kinds by model before `begin_with` stores the message. It skips the call for a command id the session already records, because that retry's ids are already `sent`.
  - The ids join the command fingerprint only when present, so fingerprints of messages without attachments are unchanged.
  - A message with attachments may have blank text. It then stores `ATTACHMENT_ONLY_CONTENT` (`[Attached files]`), so neither this daemon nor an older one after a rollback ever sends a blank user message. Clients hide exactly that text on a message that has attachments.
- **Deleting.** `delete_staged_attachment(id)` removes a staged attachment; sent ones are deleted with their conversation (`attachment_sent`). `set_attachment_excluded(id, excluded)` keeps a sent attachment out of later prompts while it stays in the transcript. Deleting a session deletes its attachment rows in the same transaction, then removes their blobs and aborts its uploads.
- **Storage.** The additive table is `attachments(id, session_id, state, created_at, size, meta, content, blob)`.
  - Plaintext columns: the ids, the lifecycle the store needs without the key (`state`, `created_at`, `size`; the id already encodes the creation time and the sealed length reveals the size) and, for blobs, a content address.
  - `AttachmentMeta` (name, kind, MIME type, size, plaintext SHA-256, pages, dimensions, state, source, command, run, message index, position, exclusion) is sealed with AAD `aidex-native-v1:attachment:<id>:<session>`. It has no `deny_unknown_fields`, so this daemon ignores fields a later one adds. A read fails closed when the plaintext columns and the sealed metadata disagree.
  - Content is sealed like artifact content, with segment AAD `aidex-native-v1:attachment-content:<id>:<sha256>:<index>:<count>`. Up to 1 MiB is stored inline; larger content goes to `<db stem>-attachments/` (`private/sessions/native-attachments/` on a drive), never to `native-artifacts/` or `tmp/`.
  - On open, without the key: rows of sessions an older daemon deleted are dropped, staged attachments older than 24 hours are deleted with their blobs, and the attachments directory is swept of temporary files and unreferenced blobs. The artifacts sweep (in this daemon and older ones) never touches that directory, and the attachments sweep never touches `native-artifacts/`.
- **Authority.** The table is the authoritative record of which message an attachment belongs to. `Run::attachments` is only a cache; older daemons drop it when they re-save a session.

## External runtimes

`RuntimeExecutor`, `RuntimeRequest` and `RuntimeEvent` are the contract for separately owned adapters. `RuntimeEvent::SessionStarted { runtime_ref }` reports a launch's native identity before its first turn can produce effects; it lives in memory only, and the harness decides what to persist. `is_resumable_reference(&runtime_ref)` is the one rule adapters and the harness share for `RuntimeOperation::Resume`: the reference must be an object with non-empty `native_branch_id` and `snapshot_digest` strings. References saved before native continuation have neither, so those conversations continue with `Start` and a transcript replay.

## Runs and forks

- `Run` records the session's `mode`, `permission_mode` and `workspace_id` when the run began (absent on older runs), so a transcript can show where a conversation switched to Agent mode. Like `skills` and `attachments`, these are optional fields of `Run`, which has no `deny_unknown_fields`.
- `Run::inference_retries` and `Run::context_trimmed_messages` are optional counters, omitted while zero:
  - `reserve_inference_retry(run_id)` uses one step of the run's budget for an inference retry and counts it, in one transaction. It is refused, with nothing written, once the run has used `max_steps` steps or is no longer active, and returns the run's retry count.
  - `record_context_trim(run_id, n)` keeps the largest number of older messages any request of the run left out of its replay view. History is unchanged, and zero writes nothing.
- `fork(source_id, ForkRequest { configuration, title, command_id })` creates a conversation whose history is a copy of the source's:
  - Assistant tool calls that never got a result are stripped in place, and only trailing empty assistant placeholders are dropped, so every message keeps its index.
  - Sent attachments are re-sealed segment by segment under the new session (new ids, same message index and order, no run or command). Their blobs are written before the transaction that inserts the session and the rows.
  - Runs, commands, checkpoints, approvals, artifacts, staged attachments and the external runtime thread (`runtime_ref`) are not copied. `SessionDetail::forked_from` records the source and the number of copied messages.
  - A fork is refused while the source has an active run, and when more than 256 MiB of attachments would be re-sealed (`too_large`).
  - With a `command_id`, a retry with the same arguments returns the conversation the first call created. The record is kept in the source's commands as `fork:<command_id>`.
