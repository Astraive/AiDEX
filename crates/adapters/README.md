# External runtime adapters

`aidex-adapters` runs external agent CLIs (Codex, Claude Code, Cursor, Grok, OpenCode, Antigravity, Pi, Muse, OMP and a generic ACP command) as `RuntimeExecutor`s for the native engine. The vendor owns its tool loop; AiDEX owns the process tree, the credentials it hands over, approval mediation where the protocol has one, and the encrypted state the vendor leaves in its home.

The daemon owns one `Arc<RuntimeManager>` (`Services::runtime()`) and keeps it across RPCs, so login processes and cancellation refer to the same jobs.

## Configuration and state

- `RuntimeConfig` is literal: an executable, bounded credential-free argv, an optional managed profile id and a `RuntimeAuth` (`none`, `vault {secret_name, env_name}` or `codex_oauth {provider_id}`). Credentials never enter it. The id `native` is reserved for the built-in loop.
- Everything the crate stores lives in `<drive>/private/` and is sealed with XChaCha20-Poly1305 under a key held in the vault as `external-runtime-encryption-key` (`RUNTIME_STATE_KEY_SECRET`, a record AiDEX manages and clients must not replace or delete). A locked vault never reads as an empty configuration.
  - `runtime-config.sealed`: the configuration list (at most 64 runtimes, 64 KiB).
  - `profile-<digest(profile)>.sealed`: a managed account's credential.
  - `account-<digest(profile)>.sealed`: that account's revision.
  - `runtime-<digest(runtime)>-<digest(session:branch)>.sealed`: a native session snapshot.
- `has_saved_configuration()` reads file metadata only, so it works while the vault is locked and never creates the key.
- `save(config)` replaces a configuration whole, `profile` and `auth` included. It refuses (`conflict`) a configuration that drops or changes the profile of a runtime whose managed account is still signed in (and that no other runtime uses): that would leave the credential on the drive with nothing to sign it out, and it is what a client saving a copy read before a sign-in or import bound the account would do. Sign out first, or apply the edit to a fresh read.
- `remove(id)` cancels the runtime's pending logins, removes its managed account (credential and revision, unless another runtime uses the profile) and its session snapshots, and only then its configuration; a removal that fails leaves the runtime configured (at worst signed out) to be removed again. It does not run the vendor's `logout`.
- `generation()` counts this manager's writes of the configuration list (saves, removals, and logins and imports that bind an account, a login from its worker thread). Executors taken before it last changed may be stale: a launch of an executor whose runtime's saved driver, profile or auth no longer match it is refused with `account_changed` (`not_found` once the runtime was removed) before anything starts, and `executors()` gives current ones.

## Process lifecycle

- Every launch gets an app-owned temporary home (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `XDG_*` and the other vendor variables point there) inside a brokered sandbox with the workspace mounted read-write. Codex always runs with `cli_auth_credentials_store="file"`, so it never reaches the host keyring.
- Launch and account homes live under one root per daemon in the host temporary folder, `<temp>/aidex-rt/d-XXXX/`, whose `daemon.lock` the daemon holds for its lifetime. A home is removed when its launch ends, the root once the runtime manager and its launches are dropped, and the shared `aidex-rt` folder with the last root (or sweep) that leaves it empty. On Unix that folder is created private to the user (`0700`); one another user owns, or that others may write to, is never used, and homes then fall back to a plain temporary folder as before. `RuntimeManager::open` first removes every root whose lock no daemon holds and whose lock file is older than a minute: what a crash, kill, power loss or pulled drive left mid-launch or mid-login (a restored managed credential, decrypted native history). Links and reparse points are never followed, an `aidex-rt` folder another Unix user owns is not swept, the sweep never fails startup, and `swept_temporary_roots()` reports only a count. `temporary_homes()` counts the homes the daemon holds now. Homes that builds before this root left directly in the temporary folder are not swept: nothing tells whose they are.
- The manager's network gate is the daemon's closure. It closes when the daemon goes offline, the vault locks or an emergency stop begins. A closed gate refuses launches and logins (`offline_refused`), and a watcher thread kills a running vendor tree within about 25 ms, also while a run waits for approval. The run's cancellation token does the same.
- **Parked approvals.** A launch paused for an approval decision stays live, with its home and the secrets handed to it, until the decision continues it. Its watcher releases it as soon as its tree ends (killed by its cancellation or the closed gate, exited, or past the 300 s wall timeout): the home with the restored snapshot and credential is removed and the secrets are dropped. `release_paused()` does that synchronously for every parked launch of every executor, also those a configuration change replaced, and returns how many it released; the daemon calls it on vault lock, emergency stop and going offline, so no decrypted state outlives a lock. `release_run(run_id)` releases one run (a cancelled, failed or abandoned run; the harness calls it through `RuntimeExecutor::release`, which `ExternalRuntime` forwards, and the daemon on `run.cancel`), and `parked_runs()` counts them. A released run stays resumable from its saved reference: a later `Resume` launches normally, and a `Resume` also supersedes a launch of its run that still waits. A `Start` for a run whose launch still waits is refused with `runtime_busy`. A decision for a released launch fails `approval_expired` (`offline_refused` while the gate is closed).
- `cancel_logins()` cancels every pending official login and leaves the manager usable, so `emergency.resume` and unlock need no restart. `has_pending_logins()` tells a lock watcher whether it has anything to stop.
- `shutdown()` is for daemon stop: it cancels logins, releases parked approvals, terminates the runtime process registry and closes it, so no runtime process starts afterwards.

## Managed accounts (Codex)

Only Codex's official account commands and portable `auth.json` format are verified. Its catalog entry lists the auth methods `native_cli` and `profile_import` (besides `codex_oauth` and `vault`); every other driver refuses account calls with `auth_unsupported`.

| Manager method | RPC | Result |
| --- | --- | --- |
| `account_status(id)` | `runtime.account.status` | `RuntimeAccountStatus` |
| `import_profile(id, source)` | `runtime.profile.import` | `RuntimeAccountStatus` |
| `login_start(id)` | `runtime.login.start` | `RuntimeLoginStatus` |
| `login_status(id, flow_id)` | `runtime.login.status` | `RuntimeLoginStatus` |
| `login_cancel(id, flow_id)` | `runtime.login.cancel` | `RuntimeLoginStatus` |
| `logout(id)` | `runtime.login.logout` | `RuntimeAccountStatus` |

`RuntimeAccountStatus = {id, driver, profile, authenticated, credential_present, evidence, status}`; `status` is `authenticated_cached`, `auth_required`, `auth_pending` or `signed_out`, and `evidence` a stable code (`native_credential_and_cli_exit_status`, `native_credential_missing`, `official_cli_login_pending`, `native_cli_logout_and_profile_removed`, `managed_profile_removed_cli_unconfirmed`). `RuntimeLoginStatus = {id, flow_id, state, profile, authenticated, authorization_url, message, error_code}` with `state` `pending`, `connected`, `cancelled` or `failed`. Neither ever carries credential bytes or vendor output.

- **Login.** `login_start` runs the configured CLI's `app-server` in an app-owned temporary `CODEX_HOME` and asks it for the ChatGPT login (`initialize`, then `account/login/start` with `type: chatgpt`); AiDEX supplies no OAuth client. The CLI opens no browser: the flow's `authorization_url` is the page its answer names (only an `https://auth.openai.com/oauth/authorize?` URL, never one carrying a code or token), and the client opens it. A browser the CLI started itself would join the login's process tree, which on Windows is a kill-on-close job, and close with it. A worker thread owns the process and its cleanup even if nobody polls; no vendor text reaches the flow. The saved configuration is not touched while the login is pending, fails or is cancelled, so the runtime keeps its previous authentication. Only once the `account/login/completed` notification of that login reports success and the CLI's `login status` confirms the credential does the worker encrypt `auth.json`, start a new account revision and switch the runtime to its profile (`profile` set, `auth: none`). A CLI that cannot start the app-server login fails the flow (`login_failed`). That confirmation runs without holding the flow, so status polls and cancellation never wait for it; a flow cancelled meanwhile saves nothing. A closed gate cancels a pending flow. A cancelled or failed flow always clears the runtime's pending state, also when its process tree could not be confirmed terminated (`process_shutdown_failed`, retried by the next cancel). One login per runtime and eight in total can be pending.
- **Import.** `import_profile` takes an explicit absolute `auth.json`, or its directory, of at most 1 MiB that is a regular file and not a link or reparse point. Only that file is read; nothing host-global is discovered. The official CLI must confirm it before it is encrypted and the runtime switches to the profile.
- **Binding.** A login or import stores the account and switches the runtime to it while the configuration list stays locked, so a runtime removed meanwhile gets no account and no configuration change lands in between. The runtime's session snapshots, and every snapshot an older daemon saved under the legacy name, are removed before the new credential is written; a failed revision rotation after that puts the previous credential back (best effort), so the runtime keeps its previous account and nothing saved under it can be resumed under the new one.
- **Status.** `authenticated` needs both a credential file and a successful official `login status` exit: cached-credential evidence, not proof of inference entitlement. The result is cached for 60 seconds per runtime, keyed by the CLI, the profile and its revision, so health checks do not start a process each time. `health` asks for it only when the binary is installed (`binary_missing` otherwise), and an account status that cannot be read leaves the runtime unverified instead of failing the check. `health` reports only its own codes: a confirmed account is `installed_auth_unverified` with `authenticated` (`ready` once the model probe answers), and `auth_required`, `auth_pending` and `signed_out` are `auth_required` (`RuntimeAccountStatus::health_status`). While a launch of the managed account is live, `health` reports the last model-list probe's result instead of starting another process with the same rotating token.
- **Logout.** Runs the CLI's `logout` on the restored credential, then removes the encrypted profile, every session snapshot of the runtime and every snapshot an older daemon saved under the legacy name, so no session restores the old credential. The runtime stays in profile mode and is signed out. A runtime without a managed profile has nothing to sign out: `invalid_request`, before anything runs or is removed.
- **Using the account.** In profile mode the profile record is the only credential and it outranks any credential inside a session snapshot (session snapshots of a profile runtime leave `auth.json` out). A signed-out profile fails `auth_required` before a process starts, and a pending login refuses turns with `auth_pending`. Exact reflections of the credential values restored at launch, and of a credential the CLI refreshed once AiDEX has read it, are scrubbed from each vendor frame and again from the completed message. This is best effort: streamed fragments of a value split across frames still reach the live events, and a refreshed token is caught only from the next frame on.
- **Refreshes.** The CLI rotates the refresh token, and a reused one is rejected. Each launch restores its own copy, so a refresh is saved as soon as the launch's watcher sees it (polled every 250 ms, and at the first turn output, an approval request, completion, a failure and after a model-list probe), and only over the credential that launch started from: once another launch of the account saved a newer one, or the account revision changed or it was signed out, the launch saves nothing more. A launch of the account waits (up to 30 s, or until it is cancelled) while another launch of it is still starting, until that one's first turn output, its first saved refresh or its end, so it restores the credential the other one refreshed. A refresh the CLI makes later in a turn (after a rejected request) is not covered by that wait; saving it at once keeps the window short.
- **Revisions.** A successful import or login starts a new account revision and removes the runtime's session snapshots (see Binding). A token refresh keeps the revision.

## Native continuation

- **Checkpoint.** Before a turn can produce effects the adapter snapshots the vendor home and reports `RuntimeEvent::SessionStarted { runtime_ref }`: Codex, Muse and ACP once the native session or thread id is known and before the turn is sent, Claude Code and Cursor on the first root `session_id`. A crash mid-turn therefore still leaves a reference to resume. A callback that returns `Pause` refuses the turn. Pi and OMP have no native restore, so they take no snapshots and report no checkpoint; their references are never resumable.
- **Reference.** `runtime_ref` carries `runtime_id`, `session_id`, `run_id`, `native_session_id`, `native_turn_id`, `native_branch_id`, `snapshot_id`, `snapshot_digest` (of the snapshot plaintext), `account_revision`, `config_digest` (driver, profile and auth configuration) and `credential_binding`; an approval request's reference adds `native_request_id` and `approval_digest`. The snapshot is refreshed at every approval request and at completion.
- **Redaction-stable.** The harness keeps a reference only when `aidex_events::redact_text` leaves it unchanged, so every field is value-free metadata and no key with a string value names a credential (`secret`, `token`, `key`, `auth`, `credential`, `password`). Tests assert this for every driver and credential kind at each point a reference is emitted.
- **Branches.** The branch is the run that started the native session, so a root conversation and each child run have independent snapshots, and follow-ups of a branch keep its snapshot name. A branch nothing continues any more is reclaimed with `forget_snapshot(reference)`, by the daemon (a thread a configuration change ended, a deleted conversation) or by the harness through `RuntimeExecutor::forget`, which `ExternalRuntime` forwards here (a reference a refused follow-up cleared, a child run that ended), and removes only a branch snapshot of the reference's own runtime (`runtime-<digest(runtime_id)>-<64 hex>.sealed`), and `forget_legacy_snapshot(runtime, session)` for an older daemon's snapshot of a deleted conversation. `remove(id)` removes the runtime's snapshots with its configuration and managed account.
- **Resume.** `RuntimeOperation::Resume` continues only a reference for which `is_resumable_reference` holds. Every evidence failure is refused with `resume_unavailable` before any process starts: no bound branch, any field that does not match this runtime, session, account revision, configuration digest or credential binding, and a snapshot that is missing, changed or cannot be restored. A vendor that cannot reopen the saved session is refused the same way, before the checkpoint and so before any event: an error answering Codex `thread/resume`, Muse `session/resume` or ACP `session/load`, a missing or different identity, a load beyond the output bounds, an ACP agent that does not advertise `agentCapabilities.loadSession` (it is never asked to load), or a process that ends meanwhile. Cancellation, a closed gate (`offline_refused`), a locked vault and missing authentication keep their own codes. The harness then starts a new native session with the transcript for a follow-up. Pi and OMP have no native restore (`supports_resume` is false).
- **ACP load.** ACP's `session/load` answer carries no identity (`null` or `{modes, models}`): the session is the one requested, and an echoed `sessionId` must equal it. The agent first replays the saved conversation as `session/update` notifications of that session; they are dropped and do not count toward the 1024 notifications one request may buffer, so the replay never becomes the new turn's text, tool steps or transcript. Agent requests during the load are kept to be answered.
- **Recovery.** Resuming the run the reference was saved by sends an inspection-only continuation: the vendor is told to inspect its history and the workspace, the original request is quoted as evidence only, and it is never sent again. A follow-up run sends what the harness gives it: its new message alone, or, when more than one message reaches it (a turn after the thread's last completed one ended early), those messages as context the native thread has not seen, marked as possibly partial.
- **Approval ids.** Vendors number their requests per connection, so a later launch of the same run (a recovery resume) reuses wire ids. `ApprovalRequest.request_id` is scoped to its launch (`<launch>:<wire id>`), so a decision of an earlier launch never matches; the reference's `native_request_id` keeps the wire id, and only the reply uses it. An approval continuation's completed message is the whole native turn, text streamed before the pause included.
- **Credential binding.** The binding is value-free. In the reference it is `{"kind":"none"}`, `{"kind":"vault","record":<digest of the vault record id>,"revision":<n>}` for a vault credential's `SecretVersion`, or `{"kind":"codex_oauth","account":<hash>}` for the shared OAuth account's `AuthService::account_binding` hash of verified issuer, subject and client. It is captured at launch, the vault credential is resolved only at that revision, and the binding is checked again right before the process starts and before an approval decision is sent. Token refresh keeps the OAuth binding; signing in to another account or replacing the vault secret changes it.

## Snapshots

- Session snapshots use the `base64_v1` archive (`{"format":"base64_v1","files":{path: base64}}`): at most 4 MiB of raw files, 4096 files and 32 directory levels, inside the 8 MiB encrypted-record cap. Links and Windows reparse points (junctions included) anywhere in the home are refused.
- SQLite databases are copied with the backup API, so a database in WAL mode is captured coherently with its committed transactions; its `-wal`, `-shm` and `-journal` sidecars are rebuilt rather than copied. A database that stays locked for 3 seconds fails the capture (`state_busy`) and nothing is published.
- Codex's top-level `.tmp` (regenerated argv0 tool copies, including Windows byte-range locked files) is left out. Other drivers have no implicit exclusions.
- A snapshot that cannot be saved (`state_limit`, `state_busy`, `state_unavailable`, `state_corrupt`, `vault_locked`) never fails a turn whose vendor work already ran. The turn completes or pauses with a reference that is not resumable (`snapshot_digest` and `native_branch_id` null, `snapshot_error` set to that code) and the stale snapshot is removed; the next follow-up then starts with the transcript. At the first checkpoint the turn continues without one.
- Account profile records keep the legacy archive (a JSON map of path to byte array) and hold only `auth.json`.

## Protocols

- Pi and OMP model ids are provider-qualified (`provider/model`), the form `begin` selects, so discovered models can be chosen.
- A Claude Code or Cursor subagent's result, failed or not, never ends or fails the root turn, and a root `session_id` that changes within a launch is a `protocol_error`.
- Vendor frames are scrubbed of every credential handed to the process, in string values, object keys and numeric or boolean reflections, and a turn's completed message is scrubbed again as a whole, for a value split across streamed fragments. The fragments themselves are not: per-frame scrubbing is hygiene, not a boundary against a full-access vendor that holds the credential. Approval arguments are redacted again before they reach callers.
- A process that ends early reports `process_closed` with its exit code, stderr byte count, a truncation flag and a closed stderr category (`assertion_failed`, `dependency_missing`, `access_denied`, `syntax_error`, `sandbox_helper_failed`, `vendor_output_withheld`, `none`), never vendor output.
- JSON-RPC `-32602` maps to `protocol_parameters`; messages mentioning auth or login to `auth_required`.

## Installer

`install(driver, source)` places only a component the drive's `runtime-components.json` declares. Every path component of the source and of `runtimes/<driver>/` is checked for links and reparse points, so a planted junction cannot redirect the write outside the drive. The artifact (at most 256 MiB) is hashed while it is copied into a temporary file in the destination directory, and only a matching digest is synced and published with a no-clobber rename. On Unix the placed copy gets the source's permission bits plus owner read, write and execute (the staging file starts as `0600`); a drive that keeps no modes (FAT, exFAT) may refuse the change while its mount already grants execution, so only a copy its owner still cannot execute fails (`installer_unavailable`).

## Rollback

- A daemon from before `base64_v1` cannot decode the new session snapshots, and it does not know the branch-scoped names. After a rollback its resume of those sessions fails closed; their conversations continue with a transcript. The snapshot an older daemon kept under `runtime-<digest(id:session)>.sealed` is removed after the first new snapshot of that session; nothing resumes from it any more.
- In profile mode an older daemon seals the whole home, `auth.json` included, under that legacy name, and the name does not tell which runtime it belongs to. So a sign-out, a login or import (an account change) and the removal of a signed-in account remove every legacy-named snapshot, of any runtime. This daemon never restores them; an older daemon would restore the previous account's credential from one on a resume after another rollback.
- Profile records stay in the legacy encoding, so an older daemon still restores a managed account. It ignores the account revision record, and it never saves a credential Codex refreshed: each of its launches restores the stored one into a fresh home that is discarded afterwards. Codex rotates the refresh token and rejects a reused one, so once Codex refreshed under an older daemon, that daemon's later launches fail `auth_required`, and after rolling forward the account must be signed in again.
- References an older daemon saved have no `native_branch_id` or `snapshot_digest`, so they are never resumed; those conversations continue with a transcript.

## Tests

`tests/process_protocols.rs` drives real processes: `tests/peer.py` speaks every protocol (scenarios select approvals, crashes, oversized native history, credential reflections, spec-shaped ACP loads with history replay, a rotating refresh token and more, and every start is recorded in `launches.txt`), and `tests/account_peer.py` behaves like the official account commands (`login status`, `logout` and the app-server ChatGPT login; it fails any run of the browser-opening `login`) without network or real credentials. Set `AIDEX_TEST_PYTHON` to the Python interpreter. The sandbox helper `aidex-sandbox-exec` must be built in the same target directory. The probes against an installed Codex are `#[ignore]`d and need `AIDEX_TEST_CODEX`; they never log in or start a model turn.
