# Rust crate boundaries

## Workspace foundation

The Cargo workspace contains only code that has a concrete implementation today:

- `aidex-core` owns small cross-domain value types and the versioned contract DTOs: `EntityId` (with `EntityId::generate(prefix)` for prefixed ULIDs from the OS RNG), `Timestamp` (with `Timestamp::now()` and chronological ordering), `WorkspacePath`, `SecretRef`, `ServiceError`, and the shared `CancelToken` (flag plus optional deadline). It has no domain or platform dependencies.
- `aidex-drive` validates portable relative paths, defines the schema-v2 root-level `aidex-drive.json` manifest (with an explicit, backed-up migration from v1), provides safe init/status operations that create only manifest-declared directories (`status_with` reports developer folders without the removable check), exposes `DrivePaths`, the resolver services use for their drive directories, and lists mounted volumes (`list_volumes`, `volume_for`) with capacity, filesystem, AiDEX manifest state, and attachment (`RemovableStatus`: removable, USB-attached fixed disk, fixed, unknown; only the first two outside the system volume are accepted by `init`).
- `aidex-host` reports compile-time platform identifiers, best-effort process paths, PATH-visible tools, and (through `sysinfo`'s safe API) total/available RAM, physical/logical cores, and the CPU model; GPU discovery (`nvidia-smi`, or the Apple Silicon GPU as a platform fact) is an explicit opt-in probe. It never configures the operating system.
- `aidex-events` is the event contract: a closed typed catalog (`EventKind`, `{"type": "<dotted.name>", "data": {...}}`, see `protocol/events/README.md`), version-2 envelopes, one strictly increasing cursor per drive in a durable SQLite log, filtered replay, retention that reports expired cursors instead of gaps, subscriptions that page history from disk then deliver live events through a bounded queue (lagging subscribers catch up from disk; publishers never block), credential redaction (`redact_text`) and size bounds on every text field, and the `EventSink` trait (`MemoryEventSink`/`NullEventSink` for tests) through which domain crates emit. It depends only on `aidex-core` and embedded SQLite. `aidexd` keeps the log at `DrivePaths::sessions()/events.sqlite3`, emits `daemon.started`/`daemon.stopping`, and serves `events.replay`, `events.latest`, and the `events.subscribe` stream; `aidex events tail --follow` reconnects and resumes after its last printed cursor.
- `aidex-storage` uses embedded SQLite for transactional state (WAL, full synchronous commits, schema versioning, and one-time import of legacy file values) and SHA-256-addressed files for large artifacts. SQLite provides atomic metadata transactions without a service; blobs are synced before atomic rename and verified on read. The selected root and every managed path beneath it must be real directories or files (symlinks are rejected); host-owned ancestors such as macOS `/var` are resolved by the OS. This local persistence is not encrypted.
- `aidex-sessions` is the durable session store (`DrivePaths::sessions()/sessions.sqlite3` plus an `aidex-storage` blob store): sessions with an explicit state machine whose transitions emit `session.*` events through `EventSink` (outbox-backed, so a lost append becomes an explicit event gap), messages, tool calls, approval references bound to intent fingerprints, typed content-addressed artifacts, hash-verified logical checkpoints with fallback past a corrupt latest one, branching, startup recovery (active sessions become `interrupted`, running tool calls `lost`), resume plans that list what cannot be recovered, and salted per-drive host fingerprints. Persisted text is redacted as defence in depth; records hold no absolute host paths. See `crates/sessions/README.md`.
- `aidex-sandbox` negotiates fail-closed OS process isolation (levels, mounts, network mode, resource limits) into an auditable `EnforcementPlan`, launches programs through its `aidex-sandbox-exec` helper (which must ship next to `aidexd`), and tracks every live process tree in a `ProcessRegistry` for cancel, shutdown, emergency stop, and drive removal. Windows uses Job Objects (level 1 maximum); Linux uses Landlock, rlimits, and namespaces (level 2); macOS uses `sandbox-exec`. It depends only on `aidex-core` plus safe OS binding crates; see `crates/sandbox/README.md` for the enforcement matrix.
- `aidex-policy` evaluates normalized action intents into allow/deny/sandbox/rate-limit/approval decisions: immutable hard safety rules, deny-wins layer precedence (global → session), built-in Safe/Balanced/Autonomous/Offline Secure profiles, tightening-only privacy, network, host-trust, and project-rule floors, closed-schema TOML policy files, conservative shell/network classifiers, and SHA-256 intent fingerprints. It is pure (no I/O during evaluation) and does not enforce anything; enforcement and approvals belong to the broker.
- `aidex-vault` is the portable encrypted vault (Argon2id → KEK → random master key; HKDF subkeys; XChaCha20-Poly1305 records and encrypted index; HMAC header; optional recovery key; atomic crash-safe writes; encrypted backup/restore) with scoped, expiring, revocable secret handles for `provider:`/`mcp:`/`process:`/`git:` consumers. `VaultService` is the daemon-owned, auto-locking wrapper; handle issuance/resolution are Rust APIs for the broker, not IPC methods. Independent security review is pending (`crates/vault/FORMAT.md`).
- `aidex-providers` owns model providers: provider-neutral chat contracts (`ChatRequest`, `StreamEvent`, `ChatResponse`), the synchronous `ModelProvider` trait, a deterministic scripted `FakeProvider`, an OpenAI-compatible HTTP provider (`ureq` + rustls, SSE streaming, tool calls, JSON-schema output, cancellable), first-class `ProviderError` outcomes, request-time credentials through a `CredentialResolver` (the daemon resolves single-use vault handles for `provider:<id>`), the `OfflineMode` egress gate that refuses remote traffic before any socket opens, and the `ProviderRegistry` persisted in `private_config/providers.toml` (secret names only). It depends only on `aidex-core` and `aidex-drive`.
- `aidex-router` selects a model for a task from provider listings: privacy mode, offline state, and secret-heavy tasks exclude remote models; context, tool, JSON-schema, and RAM needs filter; roles and the default model rank; explicit overrides are honoured or refused, never swapped. `run_with_fallback` retries the next candidate only for transient failures and emits `model.fallback` events, never moving from local to cloud when privacy forbids it.
- `aidex-web` owns web search and page fetch: the closed-schema `private_config/web.toml` (provider, SearXNG endpoint, vault secret *name*, result count, fetch switch), Brave/Tavily/Exa/SearXNG/DuckDuckGo-HTML search with sanitized results, and a guarded fetch (https only, plain http only to loopback, no userinfo, at most five manually followed redirects re-validated per hop, DNS resolved and pinned before connecting with private/loopback/link-local addresses refused unless named explicitly and allowed, 2 MiB body and 256 KiB text caps, readable content types only) with a dependency-free HTML-to-text extractor. `WebClient` takes a credential resolver and an egress check from its embedder; `aidexd` releases keys through vault handles for `process:web` and gates every connection on the offline switch and the broker's network policy (`web.*` methods). It depends only on `aidex-core` and `aidex-drive`; see `crates/web/README.md`.
- `aidexd` owns the local daemon lifecycle and serves backend services as JSON-RPC 2.0 methods over capability-authenticated loopback IPC (contract version 2: newline-delimited, 1 MiB lines, mandatory `aidex.handshake`, `<domain>.<verb>` methods registered on a `Router`, bounded `<domain>.subscribe` notification streams, stable error codes; see `protocol/commands/README.md`). Services are composed once into `Services` and shared with `methods/<domain>.rs` adapters. State is rooted on the selected drive; the endpoint capability is protected by Unix file permissions or the current Windows user's DPAPI credential. Methods today: `daemon.status|ping|stop`, `events.replay|latest|subscribe`, `workspace.*`, `vault.*` (the drive vault; handles stay in-process), `session.*` (durable sessions; startup recovery runs before serving), `model.*`/`provider.*`/`network.*` (provider registry, routing, offline switch; remote calls pass the broker), the broker's `broker.approval.*`, `policy.*`, `tool.*`, and `emergency.*` (a background thread expires due approvals; daemon stop terminates managed processes), and `context.*`/`memory.*`/`rules.show` (local index, search, packs, memory, and project rules; index jobs record `task.*` events), `mcp.*` (MCP server configuration, lifecycle, tools, and logs), and `web.*` (web search settings, provider catalog, test searches, and validated link opening). Workspace and vault changes record their `workspace.*`/`vault.*` events in the drive log. The crate also provides the blocking `Client` used by frontends.
- `aidex-workspace` owns workspaces: a durable registry (`private_config/workspaces.sqlite3`) of explicitly selected host directories, drive workspaces (`workspaces/<id>/tree`, drive-relative so they survive drive-letter changes), and ephemeral copies (`workspaces/ephemeral/<id>/`) with baseline, review, conflict-checked selective apply, and marker-verified discard. `ConfinedRoot`/`WorkspaceHandle` resolve workspace-relative paths so traversal, symbolic links, and junctions cannot leave the root. It depends only on `aidex-core` and `aidex-drive`; `aidexd` serves it as `workspace.*` and the CLI as `aidex workspace` (alias `aidex project`).
- `aidex-broker` is the execution broker and approval service: it plans every tool call (`aidex-tools`), builds `aidex-policy` intents from the plan's facts plus broker-verified facts (protected AiDEX paths, policy-directory writes, remote origins, the repository's push destination, stored credentials), evaluates them, and then executes under a permit bound to the plan fingerprint, creates a human-readable approval card bound to the intent fingerprint (durable SQLite store `private_sessions/approvals.sqlite3` with compare-and-set transitions, expiry, revocation, single use, and session grants), or denies. Processes run only through its `SandboxLauncher` over `aidex-sandbox` (failing closed when the required level is unavailable); secrets reach only the child process (or provider request) that needs them through short-lived vault handles; every decision and outcome is an audit event; `emergency_stop` freezes execution, kills managed processes, cancels approvals, and revokes handles. `ModelEgress` gates provider egress and credentials. See `crates/broker/README.md`.
- `aidex-tools` provides typed, workspace-scoped tools with a two-phase contract: `plan` validates closed `schemars`-generated schemas with stable errors, resolves every path through `ConfinedRoot`, computes policy facts (convertible to `aidex_policy::Intent`s) and reviewable diffs without side effects; `execute` runs only with an `ExecutionPermit` bound to the plan's SHA-256 fingerprint, re-verifies targets (conflict instead of clobbering), serializes overlapping writers, and emits `tool.*`/`file.changed`/`diff.created` events. Built-ins: `fs.read|list|glob|search|write|patch|delete`, `git.status|diff|log|show|branch|commit|push`, `shell.exec`; processes run only through the `ProcessLauncher` trait (the broker implements it over `aidex-sandbox`). It depends on `aidex-core`, `aidex-events`, `aidex-policy`, `aidex-sandbox`, and `aidex-workspace`; only the broker should hold a `ToolRegistry`. The broker serves it as `tool.*`; the native harness (`aidex-harness`) still holds its own registry until it moves onto the broker.
- `aidex-context` is the offline repository context layer: a rebuildable per-workspace SQLite index on the drive (`private_index/<workspace>/index.sqlite3`: files, line chunks with FTS5, regex symbols for seven language families, optional vectors, local git metadata) built by an ignore-aware, link-refusing walk that is incremental (size/mtime, then SHA-256), cancellable and batch-committed, and recovers a corrupt database by moving it aside and rebuilding; secret exclusion by file name and private-key content plus credential redaction on everything stored or returned; BM25, filename, and symbol search; `.aidex/rules.toml` project rules that only tighten `aidex-policy` decisions plus instruction files (`AGENTS.md`, `CLAUDE.md`, `.aidex/instructions.md`); inspectable session/workspace/user memory (TOML in `private_memory/`) that refuses secret-like text; and budgeted context packs whose items are wrapped in nonce-bound untrusted-data delimiters. `ContextService` runs one background index job per workspace (`task.*` events). It depends on `aidex-core`, `aidex-drive`, `aidex-events`, `aidex-policy`, and `aidex-workspace`; see `crates/context/README.md`.
- `aidex-skills` discovers portable agent skills (`<root>/<skill-dir>/SKILL.md` with YAML front matter, parsed by a small dependency-free subset parser) from the workspace (`.aidex/skills/` scope `project`; `.agents/`, `.claude/`, `.codex/` `skills/` scope `repo`), the drive's `skills/` (scope `drive`), and enabled plugins (scope `plugin`), first name wins in that order. It refuses symbolic links and junctions, caps file sizes, redacts all text, keeps enablement in `private_config/skills.toml` (drive and plugin skills enabled by default, workspace skills disabled until enabled per workspace) with `extension.*` events, and authors drive skills atomically. It depends on `aidex-core`, `aidex-drive`, and `aidex-events`; `aidexd` serves it as `skill.*` and the CLI as `aidex skills`. See `crates/skills/README.md`.
- `aidex-plugins` installs portable plugin bundles of skills and MCP servers (Claude Code plugin layout compatible; never native code AiDEX runs): manifests (`aidex-plugin.json` or `.claude-plugin/plugin.json`), bounded link- and traversal-refusing install from a folder or `.zip` into `plugins/<name>/` (32 MiB, no undeclared executables), a deterministic SHA-256 tree hash, closed-schema provenance in `private_config/plugins.toml`, trust bound to the exact tree hash (a changed tree revokes trust and disables the plugin), review contents (skills, MCP server commands without environment values), and `PluginStore::enabled_contributions` for skills and MCP discovery. It depends on `aidex-core`, `aidex-drive`, and `aidex-events`; `aidexd` serves it as `plugin.*` and the CLI as `aidex plugins`. See `crates/plugins/README.md`.
- `aidex-mcp` manages MCP servers: one closed-schema TOML file per server in `DrivePaths::mcp()` (literal launch parameters and vault secret *names*, disabled until enabled), a read-only `.mcp.json` importer that yields disabled entries without any value, an MCP JSON-RPC client over stdio (newline-delimited, 1 MiB frames) and Streamable HTTP (JSON or SSE responses, no redirects) with bounded timeouts, and a supervisor (`stopped|starting|running|failed|needs_auth`) that starts servers on demand, lists and calls their tools, and keeps a scrubbed stderr ring buffer. Stdio servers run through `aidex-sandbox` with a cleared environment and vault secrets for consumer `mcp:<id>`; `aidexd` launches them through the broker's sandbox (emergency stop and shutdown kill them), gates remote servers on the offline switch and a `network.request` policy decision, and serves `mcp.*`. It depends on `aidex-core`, `aidex-drive`, `aidex-events`, `aidex-sandbox`, and `aidex-vault`; see `crates/mcp/README.md`.
- `aidex-adapters` runs external agent CLIs (Codex, Claude Code, Cursor, Grok, OpenCode, Antigravity, Pi, Muse, OMP, and a generic ACP command) as `RuntimeExecutor`s, the contract in `aidex-native-sessions` that the native harness drives for conversations on an external runtime. The vendor owns its tool loop; AiDEX owns the sandboxed process tree (an app-owned temporary home per launch, and a network gate that refuses launches and ends running vendor processes when the daemon goes offline, the vault locks, or an emergency stop begins), the credential it hands over at launch, approval mediation where the protocol has one, continuation bound to saved native evidence, and the vendor state it keeps sealed under a vault-held key. `RuntimeManager` holds the sealed runtime configuration, managed Codex accounts (official login, profile import, sign-out), and the runtime process registry; `aidexd` owns one and serves it as `runtime.*`. It depends on `aidex-core`, `aidex-auth`, `aidex-events`, `aidex-providers`, `aidex-sandbox`, `aidex-native-sessions`, and `aidex-vault`; see `crates/adapters/README.md`.
- `aidex-cli` (`aidex`) is the command surface: clap definitions in `cli.rs`, one handler module per domain under `commands/`, a global `--json` flag, and stable exit codes (`exit.rs`, documented in `apps/cli/README.md`). Daemon-backed commands connect with `commands::daemon::connect`; `chat`/`run` still delegate to Oh My Pi.
- `aidex-bundle` is the portable bundle contract: the closed-schema `bundle.json` manifest, its detached Ed25519 signature `bundle.sig` and the compiled-in `TrustStore` (release keys, build-time keys, revocations), the drive's atomic `app/current.json` pointer (one entry per target, with the previous bundle as rollback candidate), the update journal `app/update-journal.json`, integrity and signature verification (`resolve_active`, which the launcher runs before executing anything), deterministic `.zip`/`.tar.gz` archives behind the `archive` feature, and crash-safe installation onto a drive (`install_with`/`install_signed`, staged on the drive and switched atomically). It depends on `aidex-core` and `aidex-drive`.
- `aidex-launcher` is the drive-root launcher (`AiDEX.exe`, or `./aidex` -> `app/launcher/<target>/aidex-launcher`): it finds the drive from its own path, verifies the drive manifest, the active bundle's signature against the keys compiled into it, and its critical binaries, and runs the bundle's `aidex` with `AIDEX_DRIVE_ROOT` set and the bundle's `bin/` first on `PATH`. It writes nothing and extracts nothing.
- `aidex-packager` is the developer/CI tool that builds verified bundles (`cargo build --release --locked`, license metadata and a CycloneDX 1.5 SBOM from `cargo metadata`/`Cargo.lock`, `bundle.json`, archive, `SHA256SUMS`), generates dev/CI keys, signs and verifies bundles, installs them onto drives, and smoke-tests them; it is never shipped. See `portable/packaging/README.md`.
- `aidex-updater` runs signed updates as a journalled state machine (stage → verify → self-test → atomic switch → commit) with crash recovery (roll back or roll forward to a valid version), rollback, SemVer downgrade rules, pruning to current + previous, integrity/SBOM status, and the CycloneDX model; `aidexd` serves it as `update.*` and recovers interrupted updates at startup, and the CLI exposes `aidex update …`. It depends on `aidex-bundle`, `aidex-drive`, `aidex-core`, and `aidex-events`.

The daemon uses `aidex-drive` for the selected root. The CLI links the daemon IPC client and exposes `aidex daemon start|status|stop`, `aidex events tail|show`, `aidex vault`, `aidex workspace`, `aidex session`, `aidex index`, `aidex search`, `aidex context pack`, `aidex memory`, `aidex rules`, and `aidex mcp`; the `aidexd` executable remains the lifecycle owner.

Dependency direction is inward toward small shared primitives: `aidex-core` has no AiDEX dependencies; `aidex-drive` depends only on `aidex-core`; `aidex-policy` depends only on `aidex-core`; `aidex-sessions` depends on `aidex-core`, `aidex-drive`, `aidex-events`, and `aidex-storage`; `aidex-context` depends on `aidex-core`, `aidex-drive`, `aidex-events`, `aidex-policy`, and `aidex-workspace`; `aidex-events` depends only on `aidex-core`, and domain crates emit through its `EventSink` trait; `aidex-providers` depends only on `aidex-core` and `aidex-drive`, and `aidex-router` on `aidex-providers`; `aidex-broker` composes the policy, tools, sandbox, vault, workspace, events, and providers contracts and owns the registry behind `tool.*`; `aidex-storage` depends on embedded SQLite and SHA-256 primitives; `aidexd` composes infrastructure and domain crates; and `aidex-cli` depends on `aidexd` only for its client and DTOs. Domain crates should depend on lower-level contracts, never on the executable or UI. Avoid cycles; express cross-domain events at domain boundaries.

## Requested future domains (not Cargo packages yet)

These names reserve architecture concepts, not implemented crates. Add a package only when it contains a real API and behavior with a clear owner and dependency contract.

| Domain | Intended responsibility |
| --- | --- |
| `runtime` | Own lifecycle and coordination of local runtime services. |
| `inference` | Define inference requests, results, and execution orchestration. |
| `context` | Implemented as `aidex-context` (`crates/context`); see above. |
| `memory` | Implemented in `aidex-context` (`crates/context`, `MemoryStore`). |
| `indexing` | Implemented in `aidex-context` (`crates/context`, `Index`). |
| `chat` | Own conversation/message domain behavior and APIs. |
| `harness` | Define controlled execution environments for agent work. |
| `agent-adapters` | Implemented as `aidex-adapters` (`crates/adapters`); see above. `crates/agent-adapters/README.md` points there. |
| `tools` | Implemented as `aidex-tools` (`crates/tools`); see above. |
| `mcp` | Implemented as `aidex-mcp` (`crates/mcp`); see above. |
| `skills` | Implemented as `aidex-skills` (`crates/skills`); see above. Invocation is wired by the native harness. |
| `plugins` | Implemented as `aidex-plugins` (`crates/plugins`); see above. |
| `broker` | Implemented as `aidex-broker` (`crates/broker`); see above. |
| `vault` | Implemented as `aidex-vault` (`crates/vault`); see above. |
| `identity` | Represent users, principals, and authentication identity. |
| `approvals` | Implemented by `aidex-broker` (`crates/broker`, module `approvals`); `crates/approvals/README.md` points there. |
| `remote` | Define remote connectivity and synchronization contracts. |
| `cleanup` | Own safe cleanup of managed temporary and retained resources. |
| `updater` | Implemented as `aidex-updater` (`crates/updater`); see above. |

A likely dependency shape is shared core types → policy/identity/contracts → domain services → adapters/providers/transports → runtime composition and `aidexd`. Security-sensitive `vault`, `sandbox`, `approvals`, and `policy` contracts must be designed before callers rely on them. This table is a boundary map only; it does not promise those services exist.
