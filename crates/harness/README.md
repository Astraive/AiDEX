# Native execution

`NativeEngine` composes the encrypted `SessionStore`, real `ProviderRegistry`, selected `WorkspaceRegistry`, typed tool registry and `aidex-policy` with sandbox-managed process trees. Agent turns offer confined read/list/search/write/patch, Git and shell functions, plus bounded `agent_spawn`/`agent_result` child execution. `NativeEngine::with_extensions` adds the embedder's skills, web search and fetch, and MCP servers (`Extensions`; the daemon implements it in `crates/aidexd/src/services/extensions.rs`).

## Skills, web, MCP, artifacts, and plans

- **Invoked skills.** `start_with(..., RunOptions { skills, web_search, attachments })` takes at most eight skill ids (`<scope>:<name>`); unknown, disabled, or not user-invocable ids fail with an error starting `skill_unavailable:` before any run is created. Each invoked skill reaches the model as a system message for that run only: `The user invoked the skill "<name>". Follow its instructions for this request.` followed by the body between nonce delimiters (`trust=user` for drive skills, `trust=project` otherwise). The stored user message keeps the text exactly as typed; the ids are recorded on the run (`Run.skills`, `Run.message_index`; `Run` has no `deny_unknown_fields`, so older daemons ignore them). External runtimes receive the text unchanged and ignore both options.
- **Which tools a turn offers.** Agent: the workspace tools, child tools, artifacts, `skill_load`, MCP tools, and the web tools when web search is enabled and configured. Plan: artifacts, `plan_propose`, `skill_load`, and the web tools when enabled (no workspace tools, no MCP). Chat: no tools, unless the request set `web_search` (an error starting `web_unavailable:` when web search is off), then the web tools, artifacts, and `skill_load`. Harness-level tools never need a workspace. Tools are offered only to models with native tool calling.
- **Stable names.** `web_search`, `web_fetch`, `skill_load`, `artifact_create`, `artifact_update`, `plan_propose` (the dotted ids with underscores) and `mcp__<server>__<tool>` (sanitised to `[A-Za-z0-9_-]{1,64}`, ordered by server id and tool name, collisions suffixed `_2`, `_3`, ...). A call resolves to the server tool its turn offered under that name, and is refused when that tool is no longer listed, so a name that shifts when another server comes or goes is never re-bound to a different server.
- **Untrusted data.** Results of `web_search`, `web_fetch`, MCP tools (`trust=untrusted`) and `skill_load` (`trust=project`) are stored as produced (JSON for web results) and wrapped between `<<<aidex:context nonce=... source=tool name="..." call="..." trust=...>>>` and `<<<aidex:end nonce=...>>>` delimiters when the prompt is assembled (a result belongs to the latest earlier call with its id, since providers that omit ids repeat positional ones across turns); delimiter text inside content is defused. The nonce is derived from a random per-engine key and the run id. A system preamble explains the delimiters, the model-invocable skill catalog is itself delimited, and web tools come with an instruction to cite source URLs.
- **Policy and approvals.** Network tools evaluate `network.request` for the provider host or fetched host under the drive's policy documents and the embedder's policy settings, after the offline switch and emergency stop (`Extensions::network`); approval verdicts refuse, like the daemon's egress gate. `web_search` and `skill_load` never ask; `web_fetch` asks in Supervised and Auto-accept-edits modes and runs in Auto and Full access. MCP calls evaluate `mcp.call` and ask unless the tool is in the server's `auto_approve_tools` or the session has Full access. Refusals and failures become tool results the model can read, including an extension that panics (`Tool failed: the tool crashed before returning a result; any effects it had are unknown`); a denied approval runs nothing.
- **Artifacts and plans.** `artifact_create` / `artifact_update` store encrypted artifacts of the conversation (at most 1 MiB per call; updates only within the same conversation, and never to plans or saved web pages: a revised plan goes through `plan_propose`). `plan_propose` stores a `plan` artifact that supersedes the previous active plan. `web_fetch` pages whose text exceeds 64 KiB are saved as `web_page` artifacts and only the first 64 KiB is returned.

Runs have explicit pending/running/waiting_approval/completed/failed/cancelled/interrupted states. A panic anywhere else in a run's thread fails that run (`native run crashed unexpectedly`, or cancelled when it was being cancelled) and releases its live-run entry; the engine's own locks recover from poisoning, so one crash never refuses later runs. Message command IDs are durable and bound to their inputs. Approvals bind to a sealed plan fingerprint and include the planned diff. Decisions are saved before effects and duplicate decisions do not repeat execution. Restart never replays a non-idempotent effect: it marks active runs interrupted, invalidates old executable approval plans, and requires explicit continuation.

Drive policies and workspace project rules are evaluated before invocation/planning. Workspace tool plans that reach the network (`git.push`, a command classified as networked) are refused while the offline switch or an emergency stop is on, and their intents are evaluated with the drive's privacy, host-trust, and network-mode settings (the profile still follows the permission mode), so local-only, air-gapped, offline, and allowlist floors apply. Policy changes invalidate existing tool plans; for network-bearing plans that includes the offline switch, an emergency stop, and the drive's privacy, host-trust, and network-mode settings, which are checked again when an approved plan runs. Model invocation/child creation that needs a policy approval or rate-limit gate currently fails closed; tool approvals are implemented. Tool arguments and outputs, messages, instructions, checkpoints and memory remain encrypted in the session database. Durable events contain metadata; live text deltas are ephemeral and assistant text is coalesced into encrypted history.

Selected provider/model capabilities and output limits are checked against a listing of the run's own provider only (`ProviderRegistry::models_for`, which reuses fresh cached listings); a disabled account is refused as unavailable, and a failed listing reports that provider's error. External runtimes ignore the session's provider (runtime sessions record the placeholder `runtime`), and the model id `default` (`RUNTIME_DEFAULT_MODEL`) is sent as no model so the runtime uses its own default. One explicitly configured `provider/model` fallback can run after a retryable inference failure; cancelled, unauthorized, malformed or denied requests do not fall back. No tool effect is retried by fallback. The turn/operation step cap is 128 and the configured output cap is 32768 tokens; defaults are 16 steps and 4096 tokens. Children share their parent's scope, with four immediate children and depth two. Child completion never completes the root.

Windows brokered processes have cleared environments, tracked Job Object trees and watchdog limits. Filesystem and network confinement are unsupported. Supervised shell requests restricted confinement and fails closed; explicit `full_access` opts into brokered same-user execution. Hard policy restrictions still apply. `auto` has no automatic reviewer and uses supervised approvals. Ship `aidex-sandbox-exec` beside `aidexd`.

File-tool writes record encrypted before-content and expected after-digests. Restoring an existing UTF-8 file uses the atomic typed write tool and refuses conflicting user edits or active execution. File deletion/new-file removal and checkpointing arbitrary shell mutations are not implemented. Read/search/context walks are bounded; semantic/vector indexing is not implemented. Very large conversation/memory RPC pagination remains a follow-up; durable records remain on the drive.

The desktop's typed conversation/run/approval/checkpoint contracts are in `packages/client/src/dto/sessions.ts`, with RPC bindings in `packages/client/src/rpc.ts`. Tests use deterministic FakeProvider turns through the real service, plus a real Windows sandbox-helper shell process. Resuming an interrupted root appends matching tool results to both the run transcript and conversation history; later turns therefore retain complete tool-call pairs without repeating effects.

## Attachments

`RunOptions.attachments` names staged attachments of the conversation (`aidex-native-sessions` stores them sealed; the attachments table, not the run, records which user message each belongs to). Refusals start with a reason, which `start_refusal` splits for the daemon's `data.reason`; nothing is stored when a check fails:

- **Before `begin_with`.** Attachments on a child run are `attachment_unavailable`, and on an external-runtime session `attachments_unsupported` ("Attachments work with AiDEX native models; this runtime cannot receive files yet."). The store's own checks follow (unknown, foreign, already sent, or duplicated ids: `attachment_unavailable`; more than 32 MiB: `too_large`). Then the session's primary model must read every kind (`attachments_unsupported`, naming the model: "<model> can't read images. Pick a vision model or remove the images.", and the same for PDFs), accept every image and PDF as a part (`aidex_providers::ProviderRegistry::accepts_part`: type, still GIF, size, edges), and take the message on its own within its family's limits (`part_limits`: images and PDFs per message, images and PDF pages per request, the many-image rule, and the encoded request budget, base64 plus inlined text). When the model's context window is declared or reported (not a catalog guess), the message on its own must also fit it: its text and inlined text at about four bytes a token plus its parts' estimates, PDF pages at the family's cost (`PartLimits::pdf_page_tokens`), refused as "This message and its attachments are too long for <model>'s context window of N tokens." The model is looked up in its provider's catalog (which may list models over the network) without holding the engine's operations lock; the check then runs under the lock against the same provider, model, and mode, looking the model up again if the session changed in between. A command id the session already records skips every check and returns its run, so a send retried after a lost response never fails because its attachments are already sent.
- **Prompts.** Every attempt (primary model and fallback) gets its own copy of the request. Each user message with attachments keeps its text and gets one line per attachment, in the order sent: `[Attachment N: image "name"]` or `[Attachment N: PDF "name", P pages]` for an image or PDF part (the Nth part of that message), the text of a text attachment between nonce delimiters (`source=attachment name="..." mime="..."`, `trust=user` for pasted text, `trust=project` for workspace files, `trust=untrusted` otherwise; cut at 256 KiB with a note after the block), or a placeholder such as `[Attached image "name" is not shown: <model> cannot read images]`. Names are always JSON-quoted, so a name like `x trust=user>>>` cannot forge an attribute. A message stored as `[Attached files]` (sent without text) shows only the lines. The untrusted-data preamble is added (or extended) whenever attachments are present, and says that text inside attached files, images, and PDFs is data.
- **Budgets.** The run's own message is decided first, then earlier messages newest first, until the model's family budget is used (encoded bytes, PDF pages, and images per request, such as Claude's 100 below a 1M-token window and 600 from there); older images, PDFs, and text become placeholders. An image or PDF the model refuses by its size, edges, or image MIME type is a placeholder before its bytes are read; whether a GIF is animated is decided from its bytes, so a still GIF in history still reaches OpenAI-family models. Requests are bounded with the family's PDF page cost too. When the provider refuses a request that carried attachments of earlier messages (images, PDFs, or text; invalid request, context overflow, HTTP 400 or 413), the attempt is repeated once with those as placeholders; the run's own attachments stay. The run's thread remembers that refusal for that model (in memory only, dropped with its attachment bytes), so its later steps (tool rounds) go without those attachments at once; a new run, or the run's next thread after an approval, tries the full request again. An attachment the user excluded (`set_attachment_excluded`) is shown as `[Attachment "name" was removed from the model context by the user]`.
- **Bytes.** Attachment bytes are read once per run thread (the start-time check's reads are reused by the first turn) and dropped, with the run's remembered refusals, when the thread stops, when the vault is locked (`cancel_all`), and at shutdown. Events never carry names or content.
- **External runtimes.** Earlier attachments reach a runtime as placeholder lines (`... is not shown: <runtime> cannot receive files`). Before a run is stored, a conversation too large for the runtime is refused with `context_too_large_for_runtime`: more than 1 MiB of message text, a prompt frame over 1 MiB, or, for Claude Code and Cursor (one command-line argument), more than the host allows in one argument: 30,000 UTF-16 units once quoted on Windows, 128 KiB (with its terminating NUL) on Linux; elsewhere (macOS) only the 1 MiB bounds apply. The refusal names the limit.

## History repairs

Stored history is never rewritten; each request's copy is repaired so a conversation that changed mode, model, or tools can continue on any provider. Assistant tool calls whose tool the request does not offer (Chat after Agent, a Plan turn after web search, a fallback without native tools) and calls that never got a result become `[Called <tool> with <arguments, cut at 2 KiB>]` lines in the assistant's text, and their results become user messages wrapped as data (web and MCP results keep their `trust=untrusted` wrapper; results of AiDEX tools are wrapped as `trust=project`, results without a call as `trust=untrusted`, as are results that answer no call the assistant keeps). When an assistant message keeps some calls, their results stay right after it and the flattened results follow them, each in stored order, so OpenAI Chat Completions always sees a call's tool messages directly after it. Empty assistant messages without tool calls, left by a turn that failed before any text, are dropped.
