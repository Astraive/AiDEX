# Native execution

`NativeEngine` composes the encrypted `SessionStore`, real `ProviderRegistry`, selected `WorkspaceRegistry`, typed tool registry and `aidex-policy` with sandbox-managed process trees. Agent turns offer confined read/list/search/write/patch, Git and shell functions, plus bounded `agent_spawn`/`agent_result` child execution. `NativeEngine::with_extensions` adds the embedder's skills, web search and fetch, and MCP servers (`Extensions`; the daemon implements it in `crates/aidexd/src/services/extensions.rs`).

## Skills, web, MCP, artifacts, and plans

- **Invoked skills.** `start_with(..., RunOptions { skills, web_search, attachments })` takes at most eight skill ids (`<scope>:<name>`); unknown, disabled, or not user-invocable ids fail with an error starting `skill_unavailable:` before any run is created. Each invoked skill reaches the model as a system message for that run only: `The user invoked the skill "<name>". Follow its instructions for this request.` followed by the body between nonce delimiters (`trust=user` for drive skills, `trust=project` otherwise). The stored user message keeps the text exactly as typed; the ids are recorded on the run (`Run.skills`, `Run.message_index`; `Run` has no `deny_unknown_fields`, so older daemons ignore them). External runtimes receive the text unchanged and ignore both options.
- **Which tools a turn offers.** Agent: the workspace tools, child tools, artifacts, `skill_load`, MCP tools, and the web tools when web search is enabled and configured. Plan: artifacts, `plan_propose`, `skill_load`, and the web tools when enabled (no workspace tools, no MCP). Chat: no tools, unless the request set `web_search` (an error starting `web_unavailable:` when web search is off), then the web tools, artifacts, and `skill_load`. Harness-level tools never need a workspace. Tools are offered only to models with native tool calling.
- **Stable names.** `web_search`, `web_fetch`, `skill_load`, `artifact_create`, `artifact_update`, `plan_propose` (the dotted ids with underscores) and `mcp__<server>__<tool>` (sanitised to `[A-Za-z0-9_-]{1,64}`, ordered by server id and tool name, collisions suffixed `_2`, `_3`, ...). A call resolves to the server tool its turn offered under that name, and is refused when that tool is no longer listed, so a name that shifts when another server comes or goes is never re-bound to a different server.
- **Untrusted data.** Results of `web_search`, `web_fetch`, MCP tools (`trust=untrusted`) and `skill_load` (`trust=project`) are stored as produced (JSON for web results) and wrapped between `<<<aidex:context nonce=... source=tool name="..." call="..." trust=...>>>` and `<<<aidex:end nonce=...>>>` delimiters when the prompt is assembled (a result belongs to the latest earlier call with its id, since providers that omit ids repeat positional ones across turns); delimiter text inside content is defused. The nonce is derived from a random per-engine key and the run id. A system preamble explains the delimiters, the model-invocable skill catalog is itself delimited, and web tools come with an instruction to cite source URLs.
- **Policy and approvals.** Network tools evaluate `network.request` for the provider host or fetched host under the drive's policy documents and the embedder's policy settings, after the offline switch and emergency stop (`Extensions::network`); approval verdicts refuse, like the daemon's egress gate. `web_search` and `skill_load` never ask; `web_fetch` asks in Supervised and Auto-accept-edits modes and runs in Auto and Full access. MCP calls evaluate `mcp.call` and ask unless the tool is in the server's `auto_approve_tools` or the session has Full access. Refusals and failures become tool results the model can read, including an extension that panics (`Tool failed: the tool crashed before returning a result; any effects it had are unknown`); a denied approval runs nothing.
- **Artifacts and plans.** `artifact_create` / `artifact_update` store encrypted artifacts of the conversation (at most 1 MiB per call; updates only within the same conversation, and never to plans or saved web pages: a revised plan goes through `plan_propose`). `plan_propose` stores a `plan` artifact that supersedes the previous active plan. `web_fetch` pages whose text exceeds 64 KiB are saved as `web_page` artifacts and only the first 64 KiB is returned.

Runs have explicit pending/running/waiting_approval/completed/failed/cancelled/interrupted states. A panic anywhere else in a run's thread fails that run (`native run crashed unexpectedly`, or cancelled when it was being cancelled) and releases its live-run entry; the engine's own locks recover from poisoning, so one crash never refuses later runs. Message command IDs are durable and bound to their inputs. Approvals bind to a sealed plan fingerprint and include the planned diff. Decisions are saved before effects and duplicate decisions do not repeat execution. Restart never replays a non-idempotent effect: it marks active runs interrupted, invalidates old executable approval plans, and requires explicit continuation.

Drive policies and workspace project rules are evaluated before invocation/planning. Workspace tool plans that reach the network (`git.push`, a command classified as networked) are refused while the offline switch or an emergency stop is on, and their intents are evaluated with the drive's privacy, host-trust, and network-mode settings (the profile still follows the permission mode), so local-only, air-gapped, offline, and allowlist floors apply. Policy changes invalidate existing tool plans; for network-bearing plans that includes the offline switch, an emergency stop, and the drive's privacy, host-trust, and network-mode settings, which are checked again when an approved plan runs. Model invocation/child creation that needs a policy approval or rate-limit gate currently fails closed; tool approvals are implemented. Tool arguments and outputs, messages, instructions, checkpoints and memory remain encrypted in the session database. Durable events contain metadata (tool events included, see [Native turns](#native-turns)); live text deltas and process output are ephemeral and assistant text is coalesced into encrypted history.

Selected provider/model capabilities and output limits are checked against a listing of the run's own provider only (`ProviderRegistry::models_for`, which reuses fresh cached listings); a disabled account is refused as unavailable, and a failed listing reports that provider's error. External runtimes ignore the session's provider (runtime sessions record the placeholder `runtime`), and the model id `default` (`RUNTIME_DEFAULT_MODEL`) is sent as no model so the runtime uses its own default. One explicitly configured `provider/model` fallback can run after a retryable inference failure; cancelled, unauthorized, malformed or denied requests do not fall back. Without a fallback, a transient failure is retried up to twice instead ([Native turns](#native-turns)). No tool effect is retried by a fallback or a retry. The turn/operation step cap is 128 and the configured output cap is 32768 tokens; defaults are 16 steps and 4096 tokens. Children share their parent's scope, with four immediate children and depth two. Child completion never completes the root, and a native parent waits for its active children before it completes ([Native turns](#native-turns)).

Windows brokered processes have cleared environments, tracked Job Object trees and watchdog limits. Filesystem and network confinement are unsupported. Supervised shell requests restricted confinement and fails closed; explicit `full_access` opts into brokered same-user execution. Hard policy restrictions still apply. `auto` has no automatic reviewer and uses supervised approvals. Ship `aidex-sandbox-exec` beside `aidexd`.

File-tool writes record encrypted before-content and expected after-digests. Restoring an existing UTF-8 file uses the atomic typed write tool and refuses conflicting user edits or active execution. File deletion/new-file removal and checkpointing arbitrary shell mutations are not implemented. Read/search/context walks are bounded; semantic/vector indexing is not implemented. Very large conversation/memory RPC pagination remains a follow-up; durable records remain on the drive.

The desktop's typed conversation/run/approval/checkpoint contracts are in `packages/client/src/dto/sessions.ts`, with RPC bindings in `packages/client/src/rpc.ts`. Tests use deterministic FakeProvider turns through the real service, plus a real Windows sandbox-helper shell process. Resuming an interrupted root appends matching tool results to both the run transcript and conversation history; later turns therefore retain complete tool-call pairs without repeating effects.

## Attachments

`RunOptions.attachments` names staged attachments of the conversation (`aidex-native-sessions` stores them sealed; the attachments table, not the run, records which user message each belongs to). Refusals start with a reason, which `start_refusal` splits for the daemon's `data.reason`; nothing is stored when a check fails:

- **Before `begin_with`.** Attachments on a child run are `attachment_unavailable`, and on an external-runtime session `attachments_unsupported` ("Attachments work with AiDEX native models; this runtime cannot receive files yet."). The store's own checks follow (unknown, foreign, already sent, or duplicated ids: `attachment_unavailable`; more than 32 MiB: `too_large`). Then the session's primary model must read every kind (`attachments_unsupported`, naming the model: "<model> can't read images. Pick a vision model or remove the images.", and the same for PDFs), accept every image and PDF as a part (`aidex_providers::ProviderRegistry::accepts_part`: type, still GIF, size, edges), and take the message on its own within its family's limits (`part_limits`: images and PDFs per message, images and PDF pages per request, the many-image rule, and the encoded request budget, base64 plus inlined text). When the model's context window is declared or reported (not a catalog guess), the message on its own must also fit it: its text and inlined text at about four bytes a token plus its parts' estimates, PDF pages at the family's cost (`PartLimits::pdf_page_tokens`), refused as "This message and its attachments are too long for <model>'s context window of N tokens." The model is looked up in its provider's catalog (which may list models over the network) without holding the engine's operations lock; the check then runs under the lock against the same provider, model, and mode, looking the model up again if the session changed in between. A command id the session already records skips every check and returns its run, so a send retried after a lost response never fails because its attachments are already sent.
- **Prompts.** Every attempt (primary model and fallback) gets its own copy of the request. Each user message with attachments keeps its text and gets one line per attachment, in the order sent: `[Attachment N: image "name"]` or `[Attachment N: PDF "name", P pages]` for an image or PDF part (the Nth part of that message), the text of a text attachment between nonce delimiters (`source=attachment name="..." mime="..."`, `trust=user` for pasted text, `trust=project` for workspace files, `trust=untrusted` otherwise; cut at 256 KiB with a note after the block), or a placeholder such as `[Attached image "name" is not shown: <model> cannot read images]`. Names are always JSON-quoted, so a name like `x trust=user>>>` cannot forge an attribute. A message stored as `[Attached files]` (sent without text) shows only the lines. The untrusted-data preamble is added (or extended) whenever attachments are present, and says that text inside attached files, images, and PDFs is data.
- **Budgets.** The run's own message is decided first, then earlier messages newest first, until the model's family budget is used (encoded bytes, PDF pages, and images per request, such as Claude's 100 below a 1M-token window and 600 from there); older images, PDFs, and text become placeholders. An image or PDF the model refuses by its size, edges, or image MIME type is a placeholder before its bytes are read; whether a GIF is animated is decided from its bytes, so a still GIF in history still reaches OpenAI-family models. Requests are bounded with the family's PDF page cost too. When the provider refuses a request that carried attachments of earlier messages (images, PDFs, or text; invalid request, context overflow, HTTP 400 or 413), the attempt is repeated once with those as placeholders; the run's own attachments stay. The run's thread remembers that refusal for that model (in memory only, dropped with its attachment bytes), so its later steps (tool rounds) go without those attachments at once; a new run, or the run's next thread after an approval, tries the full request again. An attachment the user excluded (`set_attachment_excluded`) is shown as `[Attachment "name" was removed from the model context by the user]`.
- **Bytes.** Attachment bytes are read once per run thread (the start-time check's reads are reused by the first turn) and dropped, with the run's remembered refusals, when the thread stops, when the vault is locked (`cancel_all`), and at shutdown. Events never carry names or content.
- **External runtimes.** Earlier attachments reach a runtime as placeholder lines (`... is not shown: <runtime> cannot receive files`). Before a run is stored, a conversation too large for the runtime is refused with `context_too_large_for_runtime`: more than 1 MiB of message text, a prompt frame over 1 MiB, or, for Claude Code and Cursor (one command-line argument), more than the host allows in one argument: 30,000 UTF-16 units once quoted on Windows, 128 KiB (with its terminating NUL) on Linux; elsewhere (macOS) only the 1 MiB bounds apply. The refusal names the limit.

## History repairs

Stored history is never rewritten; each request's copy is repaired so a conversation that changed mode, model, or tools can continue on any provider. Assistant tool calls whose tool the request does not offer (Chat after Agent, a Plan turn after web search, a fallback without native tools) and calls that never got a result become `[Called <tool> with <arguments, cut at 2 KiB>]` lines in the assistant's text, and their results become user messages wrapped as data (web and MCP results keep their `trust=untrusted` wrapper; results of AiDEX tools are wrapped as `trust=project`, results without a call as `trust=untrusted`, as are results that answer no call the assistant keeps). When an assistant message keeps some calls, their results stay right after it and the flattened results follow them, each in stored order, so OpenAI Chat Completions always sees a call's tool messages directly after it. Empty assistant messages without tool calls, left by a turn that failed before any text, are dropped.

## Native turns

- **Automatic context.** The selected workspace's file index (200 entries, three levels) and the project instruction files `AGENTS.md`, `CLAUDE.md`, and `.aidex/instructions.md` at its root are read like the model's own read-only tool calls: planned through the broker under the drive policies, project rules, and permission mode, then run with a policy permit, without events or transcript entries. A source that policy denies, that needs an approval, or that cannot be read is left out of the request; listing is evaluated as `fs.read`, so a rule denying `fs.read` drops the index too, and a rule scoped to `paths = ["AGENTS.md"]` drops only that file. The instruction files share 32 KiB, in that order, with credentials redacted and a note when one is cut, and reach the model as one system message with each file between nonce delimiters (`source=project_instructions name="AGENTS.md" trust=project`), so the preamble's project-trust rule applies. Native runs only: external runtimes load these files themselves.
- **Retries.** Without a configured fallback, a transient inference failure (unavailable, timeout, rate limited, HTTP 408, 425, 429, or 5xx) is retried at most twice, after 200 ms and 400 ms, or after the provider's `Retry-After` when that is longer and at most 2 s (a longer requested wait fails the turn). A turn whose failed attempt already streamed text is never retried, so live output is not shown twice. Cancellation ends the wait at once. Each retry uses one step of the run's budget (`SessionStore::reserve_inference_retry`, refused once the budget is spent; counted in `Run.inference_retries`) and emits `agent.retry`. Tool calls run only after a complete response, so no tool effect is repeated. With a fallback configured, its single attempt replaces the retries.
- **Replay view.** For a declared or reported context window (never a catalog or assumed one), a request that would not leave room for its output budget (at most a quarter of the window) is trimmed in its own copy: first the oldest complete groups before the current turn's user message (an assistant message with its tool results is one group, so a call never loses its result), then, while the request is over its token budget (never for the provider's message limit alone), tool results larger than a shrinking bound (8 KiB down to 64 bytes) are clipped to previews that keep the JSON shape and short fields such as paths and digests (a result wrapped as untrusted data keeps both delimiter lines and only its body is clipped), then the current turn's older groups. System messages, the context before the transcript, the current user message, user messages with attachments, the newest group with tool calls, and the last group are always kept; a user-role notice marks where messages were left out and counts toward the message limit. Stored history never changes. `Run.context_trimmed_messages` keeps the largest number of messages one request of the run left out or clipped. A request still too large fails with the context-window error before it is sent.
- **Children.** A native parent whose turn ends without tool calls while children it started are still active waits for them (reading the plaintext run index, not decrypting history), for at most the time left on its cancel token and never more than ten minutes; cancelling the parent ends the wait and cancels the children. The results it has not read yet (from an earlier such message, or from an `agent_result` call answered after the child stopped) are then added to the parent's transcript, not the conversation, as one message headed `[AiDEX child run results]`, each child's final text cut to its share of about 8 KiB, and the parent takes one more turn. The prompt wraps them as untrusted data (`source=child_results`) with the run's current nonce. A parent with no step left for that turn (its stored count, including the turn's inference retries), or whose wait ran out, completes at once and its children go on. External parents are unchanged.
- **Live output.** Text deltas of every native run, children included, are emitted as ephemeral `agent.run_delta` events carrying the run id; root runs also emit `agent.delta` for existing clients.
- **Tool events.** Workspace tools publish their own `tool.started`, `file.changed`, `diff.created`, and `tool.completed` or `tool.failed` through a sink attached when the approved or policy-permitted plan runs. Summaries, failure messages, and command lines are replaced with fixed text, so public events never carry tool arguments or results; a process's output appears only in its live, never-stored `process.output`. Process tools also publish `process.started`, `process.exited`, and live `process.output` about every 100 ms: complete lines only, never a private-key block before its end line, redacted, in chunks of at most 8 KiB. Checkpoint restores, automatic context, and desktop inspection publish nothing. A failing tool publishes `tool.failed` with a fixed message and fails the run (`task.failed` with fixed text); its arguments and error stay in encrypted history.
- **What the model reads of a tool result.** The complete `ToolOutput` (`summary`, `content`, the applied `diff`, `changes`, `warnings`) is stored as the tool result in encrypted history (the run transcript, and the conversation for root runs); events carry only paths and counts (`file.changed`, `diff.created`). Each request instead carries the envelope with `diff` replaced by `diff_stats` (each file's `path`, `kind`, `additions`, `deletions`, and `binary`, plus `files_omitted`): the unified text of a write, patch, or delete shows the file's earlier lines, which a policy denying `fs.read` keeps from the model, and it would grow every later request. The view is built per request (native prompts, external runtime transcripts, and their bounds checks) for every tool result, before it is wrapped as untrusted data, whatever call it answers: a result is never passed on whole because a call sharing its id names a web, MCP, or skill tool. Results that are not such an envelope (web pages, MCP output, errors, denials) are passed on as stored. History repairs, replay clipping, and delimiters then treat the view like any other result.
- **Repairable planning errors.** A tool call that cannot be planned for a reason the model can correct (an unknown tool name, arguments that are not JSON or fail validation, a missing file, the wrong kind of entry, a size limit, a conflict, a patch that does not apply) does not fail the run. Its result is `{"is_error":true,"code":"<reason>","message":"<redacted>","effect":"not_started"}` and the model continues; the call still uses a step. Policy denials, paths outside the workspace, forbidden, linked, or malformed paths, and other failures still fail the run.

## External runtimes

Sessions whose `runtime_id` names a registered `RuntimeExecutor` (anything but `native`) run through that runtime with the same encrypted history, step budget, and approvals as native runs.

- **Policy.** Every launch (a new message, a resumed run, an approval continuation) evaluates `model.invoke` as a remote model before the runtime request is built: an SDK may route to a cloud model, so a local-only drive policy refuses it, and approval or rate-limit verdicts fail closed. A refusal, like any other failure to build the request, leaves a new run `failed` (never `pending`) and starts no process.
- **Follow-ups.** A new root message continues the conversation's native thread with `RuntimeOperation::Resume` only when the runtime reports `supports_resume` and the saved `runtime_ref` is bound to a native branch and snapshot (`aidex_native_sessions::is_resumable_reference`). Otherwise (no reference, a reference saved before native continuation, a runtime without resume such as Pi) it uses `Start` with the conversation transcript. When the runtime refuses the reference before it starts anything, in `validate` or `execute` (`RuntimeError.code == "resume_unavailable"`: a rotated vault credential, another signed-in account, a changed or missing snapshot), the run clears the conversation's reference and starts over once with `Start` and the full transcript, bounded as a new start; a refusal after the runtime reported any event fails the run instead. Forking a conversation clears its reference (the daemon also clears it when the runtime, workspace, mode, or permission mode changes).
- **Bounds.** A `Resume` request carries only the messages from the newest user message on (`RuntimeRequest.messages`), since the native thread holds the rest, so a follow-up checks only the instructions and the new message against the runtime's limits (`context_too_large_for_runtime`: 1 MiB of text, a 1 MiB prompt frame, and the one-argument limit of Claude Code and Cursor). A `Start` checks the whole transcript, earlier attachments included as placeholder lines.
- **Native identity.** `RuntimeEvent::SessionStarted` saves the adapter's reference (at most 64 KiB, with no credential-like keys or redactable text) into the active run before the callback lets the runtime go on, and into the conversation for root runs only; a child keeps its own. It is refused after an approval pause, for a run that is no longer active, and when a second one in the same launch names a different identity. A final response without a reference keeps the last saved one.
- **Approvals.** A runtime approval request and its reference are saved in one update, which refuses a run that is not running or already has a pending approval. `approval.created` is emitted only once the run is `waiting_approval`, so a client that answers at once finds a waiting run. Answering an approval (runtime or native) checks the run status, the approval status, and the fingerprint again inside the store transaction that records the decision, so an approval that expired, or a run that was cancelled, in between is refused rather than continued.
- **Resuming an interrupted run.** `resume` needs `supports_resume` and a bound reference, and uses `Resume` with no fallback: when the runtime refuses (`resume_unavailable`), the run returns to `interrupted` with that error, because replaying the conversation could repeat effects. Sending a new message continues the conversation instead.
- **Live output.** Text deltas of every run, children included, are emitted as ephemeral `agent.run_delta` events carrying the run id; root runs also emit `agent.delta` for existing clients.

## Run lifecycle and vault locks

`completed`, `failed`, `cancelled`, and `interrupted` runs never change state through a later transition, which emits nothing for them; only an explicit `resume` moves an interrupted run back to `pending`, and a run that is no longer active is never launched. Interrupting a run expires its pending approvals (and drops the plans the engine held for them) and answers its pending tool calls, as failing or cancelling it does, and a failing parent cancels its active children first. A native run announces `agent.finished` (succeeded) only when its own transition saved `completed`; a run cancelled, interrupted, or failed just before is not reported as succeeded.

A native run that pauses for approval holds the sealed plan, then marks its live entry no longer executing, then saves `waiting_approval` together with the approval, and only then announces `approval.created`; its thread drops the entry when it ends. So reconciliation never finds the running run without an entry (or the saved approval without its plan), and an approval answered the moment it is saved relaunches the run instead of finding it still executing. The pause is saved only for a run that is still `running` and whose tokens are not cancelled: one cancelled or interrupted meanwhile (a cancel, or a vault lock and reconciliation) keeps that state, and one whose stop could not be saved (a vault that locked and was unlocked again before reconciliation) settles as `cancelled`; neither gets an approval, and the plan is dropped.

`approvals(None)` (the daemon's `approval.list` without `run_id`) lists the approvals of every conversation oldest first, by the creation time their ids encode (`approval_<ULID>`), then by conversation id, then in their conversation's order, so offset pages are strictly time-ordered and the last page holds the newest approvals. `approvals(Some(run))` keeps the same order.

`has_active()` reports whether any run has a working thread or a paused runtime process, which a vault lock must stop. `has_executing()` reports only runs that are executing: a run is marked not executing before its approval pause is saved (native or external), and again executing when an answered approval or a resume launches it; the daemon's vault keep-alive counts only these, so a run waiting for an approval never holds the vault open. A native parent waiting for its active children ([Native turns](#native-turns)) is still executing, so a child waiting for an approval keeps it counted until that wait ends (at most ten minutes). Cancelling a runtime paused for approval stops its tokens at once but stops counting it only once the cancellation is saved: an approval or resume that relaunches it meanwhile reuses the cancelled tokens (or is refused once the run is `cancelled`), so the runtime never goes on, and a cancellation that cannot be saved leaves it counted until `reconcile_after_unlock()` interrupts it. `cancel_all()` (vault lock, emergency stop) also drops every held approval plan. While the vault is locked a cancelled run's final state cannot be saved, so it stays active in the store: `reconcile_after_unlock()` then marks `interrupted` (error `Execution stopped while private records were locked; explicit continuation is required`) every active run whose thread (or paused runtime) was cancelled, and every active run without one that is not waiting on a native approval plan the engine still holds for a thread nobody stopped since (a workspace tool plan keeps the tool token of the thread that planned it), and expires its approvals. It never continues a run. A native run waiting for approval has no thread once the one that paused it ends, so `has_active()` stops counting it then; its plan stays in memory until it is answered, the run is cancelled, failed, interrupted, or resumed (which expires its approval), or `cancel_all()` drops it.
