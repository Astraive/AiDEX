# Security design constraints

AiDEX mediates agent actions rather than trusting model output. The policy and execution broker are the intended boundary for shell, process, filesystem, network, package, secret, and remote operations.

## Required properties

- Treat repository instructions, tool output, MCP results, and web content as untrusted data.
- Default to explicit scoped access; never expose the whole host filesystem or vault to an agent.
- Store durable private data encrypted and keep credentials out of logs, model context, and source-controlled manifests.
- Require authentication, replay protection, and permission scopes for remote control.
- Verify signed updates and runtime integrity before execution.
- Describe cleanup limits honestly: AiDEX controls only residue it created, not privileged host telemetry.

These properties are requirements from the product specification, not current implementation claims. The execution broker below mediates every tool call the daemon's `tool.*` methods run (the native harness still has its own policy path, see below), but neither it nor any remote boundary has had an independent security review; the vault below is pending independent security review, and the process sandbox below enforces exactly what its plans state and nothing more.

## Vault (`crates/vault`, status: implemented, independent security review pending)

- Secrets are stored in the drive's `private/vault/` directory, encrypted with a passphrase-derived key hierarchy (Argon2id → key-encryption key → random 256-bit vault master key; HKDF-SHA256 subkeys; XChaCha20-Poly1305 records and index; HMAC-SHA256 header). It does not use any host keychain, so the drive unlocks on any supported host with the passphrase or the optional recovery key. Format, validation order, crash safety, and threat model: `crates/vault/FORMAT.md`.
- Secret names, kinds, consumer policies, and values are encrypted at rest. Tampering, truncation, swapped or foreign records, missing headers, unknown versions, and symlinked paths are explicit errors; nothing falls back to plaintext or to an empty vault. Interrupted writes leave the previous committed state readable. When `vault.json` changed behind the daemon (`conflict`) or a commit of it is uncertain (`CommitUncertain`), the daemon drops its unlocked session instead of guessing: that error carries `data.session_dropped: true`, the lock cleanup below runs, and the vault must be unlocked again.
- Values leave the vault only when the broker resolves a scoped, expiring, revocable handle for a consumer the secret's policy names (`provider:`, `mcp:`, `process:`, `git:`). Model prompts, agents, sessions, logs, and shell environments can never be consumers. Handle issuance and resolution are in-process Rust APIs (`VaultService`), not IPC methods. Lock, idle auto-lock (30 min default), and daemon restart invalidate every handle. Only executing agent work counts as vault use, the same for native and external runs: a run whose thread works on it (an external run's thread drives its vendor process). The idle auto-lock waits until no run executes (`vault.lock` still locks at once). The check reads in-memory engine state at least four times per idle period (at most once a second); it never reads the vault file and never unlocks. Work that waits for a person does not count: a run waiting for an approval (native, or an external runtime paused with its vendor process) and a pending official login. So a drive left with an unanswered approval still locks after its idle period, and the lock cleanup below stops the waiting run (ending a paused vendor process and the credential it holds); the next unlock settles it as `interrupted`, and only an explicit `run.resume` continues it. One bounded exception: a native parent run waiting for its active child runs is still executing, so a child waiting for an approval keeps the vault awake through its parent until that wait ends (at most ten minutes, after which the parent completes without the child).
- Records AiDEX owns (the native record key, the external runtime state key, the app and model preferences, and `oauth.*` sign-ins) are managed: `vault.secret.list` names them in `managed`, and the generic `vault.secret.set`/`vault.secret.delete` (and so `aidex vault set|delete`) refuse them with `policy_denied` before touching the vault, so a stray delete cannot make native history undecryptable or drop a sign-in behind its service's back.
- There is no online lockout for an offline drive: passphrase strength is the protection against offline guessing. A lost passphrase without a recovery key is unrecoverable; encrypted backups protect against drive loss, not credential loss.
- `vault.init|unlock` record a drive-wide `vault.unlocked` event (vault id only). Every end of an unlocked session (`vault.lock`, an emergency stop that locks the vault, the idle auto-lock, or a dropped session) is reported once by `VaultService` outside its own locks, and the daemon then cancels native runs, aborts attachment uploads in flight, cancels pending official runtime logins, ends every external runtime process, stops MCP servers (a polling watchdog stays as a backstop), and records one `vault.locked` event (vault id only); the next unlock waits until that cleanup ran, and settles runs the lock left without a final state as `interrupted` (their approvals expire; nothing continues on its own). No daemon thread polls the vault's status for this. The one exception is `vault.unlock` while a session is open whose `vault.json` changed on disk: it replaces that session without the cleanup, because the vault never locks. Not yet done: independent cryptographic review (required before release), memory locking, zeroization of IPC request buffers, whole-vault rollback detection, audit events for secret changes and handle grants, phone factor, and host-trust policies.

## Sessions (`crates/sessions`)

- Session records must reference credentials by vault handle or `SecretRef`, never by value. As defence in depth every persisted text field (titles, messages, tool inputs and summaries, failure reasons, checkpoint labels and payloads, UTF-8 artifacts) passes through `aidex_events::redact_text` before it is written; binary artifacts are stored unchanged, and pattern-based redaction cannot recognise arbitrary secrets.
- Approvals are referenced with the intent fingerprint they approve, are never carried into a branch, and pending ones are cancelled when a session is interrupted; a resume lists them as needing a new decision.
- Host fingerprints are salted per drive (`private_config/host-salt`), never store the hostname, and read no hardware identifiers. The session database is not encrypted at rest.

## Model providers (`crates/providers`, `crates/router`)

- Provider configuration (`private_config/providers.toml`) stores endpoints and vault secret _names_ only; its closed schema rejects inline keys, and parse errors never quote file contents. API keys live in the vault with a policy naming the consumer `provider:<id>`.
- For each request the broker (`aidex_broker::ModelEgress`) evaluates `secret.use` for `provider:<id>` (a deny refuses; the vault binding of the secret to that provider is its standing approval), issues a single-use 30-second handle, resolves it, and revokes it, recording `secret.granted`/`secret.revoked`; `aidex-auth` account sign-ins resolve through `AuthService` instead; the bytes (zeroizing, redacted `Debug`) build only the `Authorization: Bearer` header and are never logged, cached, put in events or errors, or sent in the request body. A locked vault, a missing secret, or a policy that names another consumer fails before any connection is made.
- Credentials go only over `https` or to loopback; URLs with embedded credentials are rejected, and redirects are never followed so the header cannot be forwarded to another host. HTTP error text from providers (which can echo keys) is never surfaced; only status and a sanitized code are.
- Offline mode (`aidex offline on`, persisted in `private_config/network.toml`) refuses remote provider traffic before credentials are resolved or sockets are opened. Only loopback endpoints count as local; LAN servers are remote. Turning offline on applies even if persisting fails.
- The router never selects or falls back to a remote model when the privacy mode is local-only or air-gapped, the network is offline, or the task is secret-heavy; an explicit model choice that violates this is refused rather than swapped.
- Remote calls pass the offline switch and then the broker's policy: a `model.invoke` intent with remote locality and the classified host is evaluated under the active profile, privacy mode, network mode, and policy documents; approval verdicts refuse (a provider request cannot wait for a human), and an emergency stop refuses everything.
- Not yet: DNS re-checks of resolved addresses, an enforcing network allowlist, and zeroization of HTTP client buffers.

## Process sandbox

`aidex-sandbox` contains processes AiDEX launches. Callers request a level (0 direct, 1 brokered, 2 restricted, 3 ephemeral), mounts, network mode, and limits; negotiation returns an `EnforcementPlan` naming the mechanism for every requirement, or fails with the list of requirements this host cannot enforce. Nothing is silently downgraded, and level 0 requires an explicit `allow_direct` opt-in.

- Every child starts from a cleared environment plus a credential-free allowlist; credential-like names cannot be inherited, and secrets reach a tool only as explicit per-launch values that never appear in plans, logs, or `Debug` output.
- Every tree is killable as a unit (Windows Job Object, Unix process group) and tracked by a registry that cancel, daemon shutdown, emergency stop, and drive removal terminate with a per-process report.
- Windows enforces level 1 only: there is no filesystem or network confinement without unsafe Win32 calls, and process/memory/CPU limits are watchdog-enforced (sampled, tree killed on violation), not kernel-enforced. Level 1 does not contain hostile code running as the same user.
- Linux enforces level 2 with Landlock (filesystem), rlimits, and user/network namespaces when the kernel allows them; otherwise those requirements fail closed. A descendant can leave the process group with `setsid()`.
- macOS uses `sandbox-exec` profiles for write confinement and network denial; reads are not confined and the backend is validated only in CI.

See `crates/sandbox/README.md` for the full enforcement matrix and limitations.

## Supply chain: bundle integrity, signatures, SBOM, and updates (implemented)

The drive-root launcher verifies before it executes: the drive manifest (closed schema), the `app/current.json` pointer (which cannot leave `app/versions/` and pins the SHA-256 of the selected `bundle.json`), the manifest itself (closed schema, host target, version, drive schema, no host extraction), the manifest's Ed25519 signature (`bundle.sig`, over the exact `bundle.json` bytes with a domain-separation prefix) against the trust store compiled into the launcher minus revoked keys, and the size and SHA-256 of every critical binary, refusing symbolic links, junctions, and unlisted files beside the binaries. Any mismatch stops the launch with exit code 11 and nothing runs. Unsigned bundles are refused unless the host explicitly sets `AIDEX_ALLOW_UNSIGNED=1` (development; warned on every launch); an invalid, unknown, revoked, or out-of-window signature is never accepted.

- Trust roots are compiled in: release public keys (`crates/bundle/src/signature/release-keys.json`, with validity windows and revocations), plus keys baked into a specific build with `aidex-packager build --trust-key` (CI's per-job ephemeral key). Test builds alone honour `AIDEX_DEV_TRUSTED_KEYS`. No private key is committed or stored in CI; tests generate keys at run time. The release key is to be held only in a protected signing environment; none is provisioned yet (see `portable/packaging/README.md#signing-keys` for provisioning, rotation, and revocation).
- Key validity is checked against the bundle's signed `created_at`, so a possibly compromised key must be revoked (compiled-in list, or the drive's additive `manifests/revoked-keys.json`), not merely expired.
- Updates (`aidex-updater`) accept only packages signed by a key the installed AiDEX trusts, verify every file, refuse wrong targets, newer drive schemas, host extraction, unsafe or oversized archives, and downgrades (except back to the recorded previous bundle with `--allow-downgrade`), self-test the staged binaries, and switch the pointer atomically with a journal; crash recovery returns to the old or the new verified version. `SHA256SUMS` is a transfer check only; trust comes from the signature, never from the checksum file or the transport.
- Every bundle ships a CycloneDX 1.5 SBOM (`docs/sbom.cdx.json`, covered by the signature) listing every linked crate with version, purl, SPDX license, and `Cargo.lock` hash, and the shipped binaries with their SHA-256.

Limits: the trust anchor lives in binaries on the drive, so someone who can write the drive can replace the launcher itself (signatures stop modified bundles and untrusted updates from being run or installed by an intact AiDEX, not a replaced launcher). A concurrent writer could swap a file between its check and its execution. Windows loads the launcher's DLL imports from the drive root before any check runs. There are no provenance attestations, transparency log, OS code signatures, or online update feed yet, and the drive revocation list can be deleted by someone with write access (compiled-in revocations cover that).

## Policy evaluation (implemented)

`crates/policy` (`aidex-policy`) implements deterministic policy evaluation: agents' requests are normalized into intents carrying broker-computed facts, and evaluation returns allow, deny, sandbox, rate-limit, or approval with the deciding rule and a human-readable effect summary. Hard safety rules (disk formatting, raw drive writes, credential export, secret dumping, deleting root/home/system directories, vault modification, broker disabling, AiDEX-protected paths) deny unconditionally, including when a shell command implies them; policy changes and destructive commands always need one-time approval. Any layer deny wins; otherwise the most specific layer, then the active profile, then deny-by-default decides. Privacy mode, network mode, host trust, and repository project rules can only tighten a decision. Policy files are closed-schema TOML and fail closed when malformed. Intent fingerprints let approvals bind to the exact intent.

The native harness now routes typed tool plans through this decision engine, persists encrypted approvals, and checks exact plan fingerprints and current policy state before execution. Model invocation and native child creation are evaluated as well; unsupported approval/rate-limit gates fail closed. Native shell processes use `aidex-sandbox`, with the Windows confinement limits above explicitly reported. The shell classifier remains a conservative heuristic; full-access same-user execution is not a security boundary for hostile shell code. This integration has not had independent security review.

## Execution broker and approvals (`crates/broker`, implemented; review pending)

`aidex-broker` holds the registry behind the daemon's `tool.*` methods (`tool.invoke` for the local user). The native harness (`aidex-harness`, desktop agent runs) currently keeps its own registry, policy evaluation, and approvals (`approval.list|respond`); moving it onto the broker is follow-up work, so the broker's guarantees below cover `tool.*` calls only.

- Every call is planned without side effects, then evaluated as `aidex-policy` intents built from the plan's computed facts plus broker-verified ones: AiDEX's private drive directories (vault, identity, sessions, config, memory, index, runtime) are `protected` (hard-denied for every `fs.*` action), writes beneath `policies/` imply `policy.change`, remote-device origins imply `remote.action`, a `git.push` destination is read from the repository's own `.git/config` (rewrites make it unknown), and a stored credential adds a `secret.use` intent. Requests from agents, skills, adapters, and remote devices can never perform `policy.change`, `broker.disable`, `vault.modify`, `credential.export`, or `secret.dump`; the local user changes policy only through `policy.profile.set`/`policy.reload`, recorded as `policy.changed`. A policy document or project-rule file that fails to load denies every call.
- Execution needs an `ExecutionPermit` bound to the plan's fingerprint; processes start only through the broker's sandbox launcher, which refuses plans it was not told about, at the decision's level or not at all (Windows cannot provide `restricted`, so Safe-profile process tools are denied there). Rate limits are enforced per session and rule.
- Approvals are cards (effect, workspace, targets, redacted command, secret names, redacted diff, scope options, expiry) bound to a SHA-256 fingerprint of the plan without its random ids plus every intent fingerprint and the origin. Continuing re-plans and refuses any difference (`intent_changed`), re-evaluates policy, and consumes the approval once. State changes are compare-and-set SQLite updates (one winner per race); expiry runs in the background and on resolution. Session grants match only identical targets in the same session and workspace, expire, and are revocable. Raw tool input is never persisted, so pending approvals are cancelled when the daemon restarts.
- Secrets are evaluated as `secret.use`, released as short-lived handles only after the permit, resolved inside the broker, and injected only into the child's environment (git: a URL-scoped `http.extraHeader`, helpers reset, system config ignored) or the provider request header. Tests grep every event, card, record, and outcome for the injected token.
- Emergency stop freezes submissions and continuations, cancels running calls, terminates every managed process tree, revokes every vault handle and unused approval or grant, cancels pending approvals, and optionally locks the vault; daemon shutdown also terminates managed processes. The daemon's `emergency.stop` also cancels every native and external agent run and every pending official runtime login and ends every vendor process, and external runtimes launch nothing until `emergency.resume`.
- A tool process at `brokered` level runs as the same OS user and can read the daemon's endpoint capability, so it could call IPC methods as the local user (including resolving approvals); `restricted` confinement (Linux, macOS) keeps the drive's runtime directory out of reach, and Windows denies `restricted` commands. Binding approval decisions to a channel tool processes cannot reach is follow-up work.
- Not yet: authenticated remote approvals (#29), pushed approval prompts in the CLI, credential injection for process consumers other than MCP servers (which receive their `mcp:<id>` secrets at launch, see `crates/mcp/README.md`), an enforcing egress proxy, and an independent review of the broker.

## External agent runtimes (`crates/adapters`)

- Runtime configuration holds literal executables, argv, and vault secret names only, sealed with a vault-held key; a vendor process receives its credential (a vault API key scoped to the runtime, or a managed account profile) only at launch, bound to the credential revision recorded then; a changed credential refuses to resume the old vendor thread.
- Vendor processes and official logins run in the sandbox and only while the drive is online, the vault is unlocked, and no emergency stop is in effect. Going offline, any end of the vault session, and an emergency stop end the processes and logins already running within a fraction of a second and refuse new launches; going offline also cancels the active runs of runtime conversations, since a vendor process makes its own network calls. Daemon shutdown ends every login and vendor process.
- Managed accounts (Codex only) run the official CLI in an app-owned temporary home, never the host's own profile, with a file credential store. Only a credential the CLI confirmed is kept, encrypted on the drive; temporary homes are removed. Results carry status codes and the browser authorization URL, never credential bytes, imported file contents, or CLI output. An import reads only an explicitly selected absolute regular file (no links or junctions, at most 1 MiB). Signing out removes the encrypted profile and every session snapshot of the runtime. While vendor processes may not start, no account command starts the official CLI: account status and runtime health answer from the status the CLI last confirmed (no credential text), and import, login, and sign-out are refused (`offline_refused`).
- A configuration change of mode, permission mode, instructions, project, or runtime drops the conversation's saved vendor thread, so a thread started under other rules is never continued.

## Native private history

Native conversations, configuration/instructions, provider message metadata, tool arguments/results, checkpoints and workspace memory are sealed with XChaCha20-Poly1305 and record identity/version AAD. A random key is stored in the existing vault for the process-scoped native record store and resolved/revoked through short-lived handles per operation. No decrypted key is persisted in config or sent to model input. Locked vaults expose opaque IDs/status only. Restart marks active runs interrupted and continuation never blindly replays pending effects. Native durable events carry metadata; private streaming text is ephemeral, and coalesced history is encrypted. An applied diff never reaches a model: encrypted history keeps a tool's full output (its unified diff included), which the desktop shows, while every model request (native prompts and external runtime transcripts) carries the diff reduced to `diff_stats` (each file's path, kind, added and removed line counts, and whether it is binary), because the unified text shows a file's earlier lines that a policy denying `fs.read` keeps from the model. Native artifacts (metadata and bytes, inline or as blob files beside the database) are sealed with the same record key in authenticated segments bound to the artifact id and content hash; only artifact and session ids and the blob content address (a hash of ciphertext) are plaintext.

Chat attachments (images, PDFs, and text files sent with a message) are never stored in plaintext: not in files, `tmp/`, events, logs, or error messages. Their names, metadata, and bytes are sealed with the same record key under their own AAD domains, in a separate table and a separate blob directory (`<db stem>-attachments/`) that the artifacts sweep never touches. Uploads are sealed segment by segment as chunks arrive, the declared size and SHA-256 are verified at commit, and the key is resolved per chunk, so a locked vault stops an upload; every lock (`vault.lock`, an emergency stop that locks the vault, the idle auto-lock, or a session the vault drops) also deletes partial upload files as it happens. In plaintext the table keeps only ids, the lifecycle state, the creation time, and the size, which the id and the ciphertext length reveal anyway. The kind is decided from the bytes, never from the client's MIME type; text containing private key material is refused. The daemon reads no host path for an attachment except a file of a registered project, through its confined root, and refuses credential-looking names for both the requested path and a link's target. Text attachments reach models only between nonce delimiters (`source=attachment`, name and MIME JSON-quoted), at one of three trust levels: files the user picked, dropped, or pasted as files are `trust=untrusted` data; long pastes folded into a file (upload `source: "paste"`) are `trust=user`, the user's own words; and project files attached with `attachment.from_workspace` are `trust=project`, which the model follows as task guidance when it does not conflict with the user's request, policy, or approvals (unlike repository files in context packs, which are untrusted). No attachment can grant permissions, but a project file can steer the task, so attach only project files you trust. The upload `source` is declared by the client: the daemon accepts only `paste` and `file` (default `file`) and keeps `workspace` for `attachment.from_workspace`, and a client should send `paste` only for text the user pasted. Text inside attached images and PDFs is never an instruction. Image and PDF bytes reach models only through the same model egress checks as any other request (offline switch, emergency stop, policy). Sent attachments are deleted with their conversation; staged ones older than a day are deleted when the daemon starts and, on a running daemon, by the next upload, project attachment or attachment list (at most every 5 minutes). Limits: names and metadata are sealed, but sizes and timing of uploads are visible to anyone who can read the drive.

## Repository context, secret exclusion, and prompt injection (implemented)

- `aidex-context` never reads, indexes, searches, or packs files whose names look credential-bearing (`.env*`, key and certificate stores, SSH keys, `credentials*`, `secrets.*`, `.npmrc`/`.pypirc`/`.netrc`/`.git-credentials`, everything under `.ssh`, `.gnupg`, `.aws`, `.docker`), even when a pack names them explicitly. A file containing a private-key block is excluded as key material; other recognisable credentials are redacted with `redact_text` before chunks are stored, and search results, pack items, rules, and summaries are redacted again on output. Ignore rules apply to indexing (and therefore to search and packs), symbolic links and junctions are never followed, and files are re-resolved through `ConfinedRoot` before they are read. Detection is name- and pattern-based: an arbitrary secret with no recognisable shape in an ordinary file can still be indexed.
- Context packs wrap every item in `<<<aidex:context nonce=… trust=…>>>`/`<<<aidex:end nonce=…>>>` delimiters with a random per-pack nonce, so repository content cannot close or forge a delimiter; items carry `trust` (`user` for user memory, `project` for rules and instruction files, `untrusted` for repository files, agent-written memory, and summaries). The harness must include `ContextPack::preamble()` and treat untrusted items strictly as data (spec §91). Packs are assembled locally and never sent anywhere by this crate; whether one may go to a remote model is the router's and broker's decision.
- Repository project rules (`.aidex/rules.toml`) are untrusted input and can only tighten policy: they attach as `aidex-policy` project floors (`never_modify` denies writes and deletes, `require_approval` forces approval), the closed schema has no way to allow anything, and an invalid, symlinked, oversized, or root-escaping rules file is an error rather than being ignored.
- Memory is not a secret store: adding or editing secret-like text is refused, hand-edited entries that look secret-like are dropped from packs, and agent-written entries are marked as such and treated as untrusted.

## Event redaction (implemented)

- Events (`aidex-events`) reference secrets by handle and name only. Every free-text event field is passed through `redact_text` (provider tokens, JWTs, bearer/authorization credentials, PEM private keys, URL passwords, password/token/secret/key assignments) and bounded before it is stored or streamed, and an identifier that looks like a credential refuses the event. Redaction is pattern based and is a last line of defence, not a substitute for keeping secret values out of events. The event log is not yet encrypted at rest.

## Tools (`crates/tools`, implemented; brokered)

`aidex-tools` splits every tool call into a side-effect-free `plan` and a permit-gated `execute`. Plans validate input against closed schemas, resolve every path (including git pathspecs and the shell working directory) through `ConfinedRoot`, and record the facts policy needs: resolved paths with a name-based credential hint (`sensitive`), the classified command line, network use (git remotes are reported as unresolved destinations), destructive and remote-write effects, and implied actions (writes beneath `.aidex/` imply `policy.change`). A permit names the plan's SHA-256 fingerprint; execution refuses a different or altered plan, another workspace/session/call, a read-only permit for a writing tool, or a second execution. Writes re-check the target's hash under a per-path lock and fail with a conflict rather than clobber; file tools never modify `.git` (hooks there would run code). Git runs with fixed arguments, hooks and fsmonitor disabled, no pager/external diff/textconv, and `GIT_CEILING_DIRECTORIES` at the workspace root; processes are launched only through the `ProcessLauncher` trait, which the broker implements over `aidex-sandbox` (the `DirectLauncher` behind the `direct-launcher` feature is unsandboxed and for tests only). Event summaries, failure messages, and process output are redacted and bounded; tool output is untrusted data. Tools run through the broker's `tool.*` path or the native harness; `fs.read` returns file content unredacted (credential-like files are `sensitive` and need one-time approval, AiDEX's private directories are `protected` in the broker), and confinement remains a point-in-time check.

## Workspace confinement

`aidex-workspace` confines workspace-relative paths in-process (for the tools and apply logic that use it). Workspace roots are only directories the user explicitly selected (never the drive, a directory containing it, or AiDEX-managed directories) or directories AiDEX created on the drive. `ConfinedRoot::resolve` rejects traversal, absolute, drive-letter, and UNC paths, alternate data streams, and Windows reserved or aliasing names; it follows a symbolic link or junction only when the resolved target stays inside the root and fails closed on dangling or looping links. A registered host root whose path now canonicalizes somewhere else (for example because a parent directory was replaced by a link or junction) is reported unavailable and refuses every resolution, including through handles taken before the change; a bind mount that keeps the same canonical path is not detected. Ephemeral copies are applied only after review, per selected file, with conflict detection and a review digest; deletion is limited to marker-verified, AiDEX-created directories, and host data is never deleted. Resolution is a point-in-time check rather than OS-enforced isolation: a process that can modify the workspace concurrently can race it (TOCTOU), and containing untrusted processes is `aidex-sandbox`'s job (not yet wired to workspaces).
