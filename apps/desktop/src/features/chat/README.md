# Chat feature

Conversations (route `chat`, `id` = session id), composed only from `@aidex/ui`. `ChatPage` and the agent feature's `AgentPage` both render `ConversationPage` with their initial mode.

- `ConversationPage.tsx`: the conversation log (`transcript/`), approvals (the shared `approvals/ApprovalRequestCard`; each decision goes to `approval.respond` as `approvalDecision` builds it, so a truncated request can be denied but not approved), run errors, Resume task (only when `canResume` allows it), Conversation settings and Artifacts buttons (`artifacts/`) next to Execution details, and the docked compact `Composer` with mode, model, project, and web search controls, the `$` / `/` menus (`composer/`), and attachments (`attachments/`). The whole page is a `FileDropZone`. A prompt and attachments handed over from Home (`pendingPrompt`, `pendingAttachments`, both in memory) send themselves once an explicit or default model is ready, unless the model cannot read the attachments (the composer then says why). A send opens its conversation (a new chat's first send, a Chat → Agent switch) only while the page is still on screen: when the user opened another screen while attachments uploaded, a toast says the message was sent (or why not) and the screen they are on stays. `ConversationPage.module.css` keeps only its original page layout classes (`conversation`, `header`, `empty`); the attachment chip that used local CSS is gone, replaced by `@aidex/ui` components.
- `ConversationModelPicker.tsx`: `ModelPickerTrigger` and `ModelPicker` from `@aidex/ui` over the shared catalog (`useProviderCatalog()`), with favorites, provider status, and links to Providers. `Mod+Shift+M` (`MODEL_PICKER_SHORTCUT` in `lib/shortcuts.ts`) opens and closes it; runtime model lists are fetched when it opens.
- `resolveConversationModel.ts`: pure model resolution. A conversation keeps its own model, shown as Unavailable when it is no longer listed rather than replaced. A new chat uses its draft choice, then the saved default (`preferences.modelId`), then the registry default, then a running local model; it never falls back to the first listed remote model.
- `currentModel.ts`: the picker row and rail entry for the resolved model, including unlisted and hidden ones.
- `sessionConfig.ts`: full `SessionConfig` values (the daemon replaces the whole configuration) and change detection. A conversation keeps its own instructions, fallback, and limits instead of inheriting preferences; `overrides` replace them (an explicit `fallback_model: null` removes the fallback) and are checked against the daemon's bounds first.
- `sessionSettings.ts` (pure): instructions, fallback model, and step and token limits with the daemon's bounds (`SessionConfig::validate`: 1–128 steps, 1–32,768 output tokens, 32 KiB of UTF-8 instructions, a native `provider/model` fallback), shared with the Agents defaults form, and `fallbackModelOptions` (native chat models in picker order; Agent conversations only get models with native tool calling, which the harness requires of a fallback there; a saved fallback that can no longer be offered stays, marked).
- `ConversationSettingsDialog.tsx`: Conversation settings (header, sliders icon) for an existing conversation: instructions, fallback model (not for external runtimes, which take none), and the step and token limits, saved with one `agent.configuration.set` carrying the whole configuration. They apply from the next run; while a run is active the fields are disabled and a notice says why. An invalid field is focused on Save. New conversations still start from the defaults in Agents → AiDEX Native.
- `canResume.ts` (pure): Resume task is offered only for an interrupted latest run, and on an external runtime only when the engine's descriptor for it (`execution.status` `runtime_descriptors`, read through `continuation/engineCapabilities.ts` once such a run is interrupted) supports resume and the run saved a protocol reference (`has_runtime_ref`). The engine refuses everything else, including cancelled runs.
- `ModelStateNotice.tsx`: why the conversation cannot send yet (no model, unavailable model, local model stopped), with the next step.
- `ChatSidebar.tsx`: the shared `LiveSessionSidebar` (`../sessions/`): New chat, History, and Recent sessions from `conversation.list` (refreshed every 2 s; a locked conversation shows as "Locked conversation"), each opening its conversation.
- `useConversationExtensions.ts`: the invocable skills of the conversation's project (`skill.list`), whether web search is set up (`web.settings.get`), and the current status of the plans the transcript shows (the newest `artifact.list` page, then `artifact.get` for older plans, refreshed as tool results arrive; a plan card offers Implement only once its plan is confirmed active).
- `composer/`: the composer's menus and web switch.
  - `useComposerMenu.tsx` drives `@aidex/ui`'s `CommandMenu`. `$` lists enabled, user-invocable skills (ranked like t3code: name, display name, description, then scope; scope badges); with no skills it offers "Manage skills" (Extensions → Skills). `/` at the start of a line lists `/chat`, `/plan`, `/agent`, `/web`, `/new`, then skills as `/skill:<name>`. Both menus highlight their first row when they open and whenever the query changes, so Enter or Tab picks the best match rather than a row highlighted earlier. Once the query starts a command name, other commands no longer match by description. A command that can't run here (for example `/web` in Plan mode) is listed, disabled, only while the query is empty or starts its name; once the query starts its name it is the first row. A disabled row keeps the highlight like any other (as the first row, `/` alone included, or when reached with the arrow keys or the pointer): on it Enter (also with Ctrl, Alt, or Meta) and Tab do nothing and the menu stays open, instead of running a lower row, inserting a skill, or sending the text, and clicking it does nothing either. The arrow keys still reach the other rows, and Escape closes the menu so Enter sends. Text that matches a disabled command only through its description or a fuzzy match (e.g. `/context` while Plan can't run) does not list it, so Enter still sends the text, or picks a matching skill. Picking a skill inserts `$name ` and remembers the skill id; external runtimes get neither skills menu nor skill rows.
  - `composerText.ts` (trigger detection, range replacement, the skill ids a message invokes), `skillSearch.ts`, `slashCommands.ts`, and `searchRanking.ts` are pure.
  - `WebSearchToggle.tsx` and `useWebSearchToggle.ts`: the globe button. In Chat it switches web search for this conversation (window-local, carried over when the first send creates the conversation, including changes made after a failed first send); Plan and Agent always offer web tools while web search is on; without a configured provider it is disabled with "Set up web search in Extensions → Web".
- `transcript/`: how messages render. `transcriptModel.ts` (pure) pairs harness tool calls with their results by `tool_call_id`, groups consecutive web searches, and reads the harness's failure prefixes (`Tool failed:`, `Tool refused:`, denial). `Transcript.tsx` renders user messages with `$skill` chips for invoked skills, assistant replies with `Markdown` (links open through `web.open` after an http(s) check, `useOpenLink.ts`), and `WorkLogRow`s: "Searched the web" with the query (expanding to `WebResultList`; consecutive searches as "Searched the web N times"), "Read <host>" (title, link, and the saved `web_page` artifact), "<server> · <tool>" for MCP (arguments and output), and "Loaded skill <name>". `artifact_create`/`artifact_update` show an `ArtifactCard` (Open, Download); `plan_propose` shows a `PlanCard` with Copy, Download, Implement (switches to Agent and sends "Implement this plan:" with the plan), and Implement in a new chat (a new Agent chat in the same project sends it on arrival). Other tools keep their arguments and output inline. Long results are read through `history.read` when a row expands (`useFullContent.ts`).
- `attachments/`: chat attachments (contract in `packages/client/src/dto/attachments.ts`).
  - Intake (`attachmentIntake.ts`, `imagePrep.ts`, pure rules in `attachmentFiles.ts`): files come from the attach menu's "Upload from computer" (a hidden file input), paste (files when the clipboard has no plain text, and an image copied on its own, as `shouldClaimFilePaste` in `@aidex/ui` decides; rich copies such as spreadsheet cells paste as text), a drop anywhere on the page (not on an open dialog), or "From project…" (`ProjectFileDialog.tsx`: a project and a project-relative path; it does not change the conversation's project, and the daemon reads the file through the project's confined root with `attachment.from_workspace`). Kinds come from the bytes, like the daemon's sniffing: PNG and JPEG images (WebP becomes PNG when transparent, else JPEG, because some vendors such as xAI read only PNG and JPEG; GIF becomes its first frame as PNG; BMP, recognized by its info header size so text starting with "BM" stays text, HEIC, and AVIF are converted when the webview can decode them, HEIC is refused with a clear message otherwise), PDFs up to 16 MB, and UTF-8 text up to 1 MB (text with a private key is refused). What is uploaded is held in memory from intake on, never the picked `File`, which Chromium refuses to read once the file changed, moved, or was deleted on disk; an upload that still fails that way asks to remove the file and attach it again, since a retry cannot help. Images over 3,750,000 bytes or 2000 px are downscaled in the webview (`createImageBitmap` and a canvas; longest edge 2000 px; PNG first for transparent images and graphics, else JPEG on white at qualities 0.92/0.85/0.78/0.68, then at 75% and 55% scale). Previews are `data:` URLs only (the release CSP has no `blob:` in `img-src`). At most 20 attachments and 32 MB per message; duplicates (same name, size, and type) are skipped. A paste of 32 KiB or more becomes `pasted-text.txt` (`-2`, …) with a toast; Ctrl/Cmd+Shift+V keeps it inline. Refusals use t3code's wording and show in the page notice.
  - Uploads (`attachmentDraft.ts`, `useConversationAttachments.ts`): one draft per conversation, kept in a module-level map while it holds attachments, so it survives the remount after a new chat's first send and the Chat → Agent route change. Uploads are sequential: `attachment.upload.begin` with the SHA-256 (`crypto.subtle`), 256 KiB chunks in base64 (every chunk but the last exactly `chunk_bytes`), `attachment.upload.commit`, with progress in the tray. An existing conversation uploads as soon as files are added; a new chat uploads right after `conversation.create` at its first send. When an existing conversation opens without a draft in this window (after a reload, Lock drive, or a restart; this also picks up a copy whose delete failed), its staged copies come back to the tray first (`attachment.list`), as ready, newest first while they fit one message (20 attachments, 32 MB); the rest are deleted, since unseen staged copies still count against the daemon's caps (40 per conversation, 256 MB in all, refused as "Too many attachments are waiting to be sent in this or other conversations"). Uploads and sends wait for that list; if it fails (a locked vault), the copies expire on their own. Remove aborts an upload in flight or deletes the staged copy; a failed upload (shown with the reason) retries from the start. Remove and retry are disabled while a message is being sent, because the send already carries the ready ids. The draft holds that lock itself (from `uploadAll` until `markSent`, or `release` when the send fails), since the send outlives the page: a page remounted meanwhile keeps the tray, the composer, and Send disabled until the send settles. Send is blocked with a reason while attachments are prepared or uploading, when one failed, when the model cannot read images or PDFs (`model.list` `input`), and for external runtime models (attaching is disabled with "Attachments work with AiDEX native models"). A send passes the staged ids as `attachments` (the retry key includes them) and may have no text; the tray clears on success. A send refused as `attachment_unavailable` re-uploads staged copies that expired.
  - Transcript (`SentAttachments.tsx`, `attachmentImages.ts`, `attachmentDownload.ts`): user messages show `MessageAttachments`; images load lazily through `attachment.read` pages into `data:` URLs (cached per id, about 64 M characters, least recently used dropped first, except images on screen: `MessageAttachments` reports them through `onImageVisibilityChange` and they are never evicted, so tiles in view cannot evict each other in a reload loop) and open in the image viewer; other files download by assembling every page into a `Blob`. A just-sent image shows its local preview until the stored copy has been read. A message sent with attachments only stores "[Attached files]" as its text, which is hidden.
- `continuation/`: Chat to Agent.
  - `ContinueAsAgentDialog.tsx`: "Continue as Agent" for a Chat or Plan conversation with history on a native model, opened from the header (bot icon), `/agent`, or Agent in the mode dialog (a conversation without history still switches directly). It asks for a project (required; preselected from the conversation, the default project, or the only one registered; "Add a workspace"), a permission mode, a model with native tool calling on AiDEX's own harness (the conversation's model is preselected when it qualifies, even if hidden from the picker; otherwise one must be picked, and the hint says whether the conversation's model is not available right now or can't use agent tools), and an optional first instruction, and says that the agent sees this conversation's messages and attachments. It warns when the chosen model cannot read images or PDFs earlier messages carry (`attachment.list`, the agent then sees their names only). "Continue here" (focused first) sends one `agent.configuration.set` with Agent, the project, the permission, and the model, then `agent.start` with the instruction when there is one. If only that start fails, the switch stands and the dialog closes: the instruction goes into the composer (after any text there) and a toast says why it was not sent. The header action that opened the dialog goes away with the switch, so focus moves to the composer, or to the conversation heading while the started run keeps the composer disabled (without scrolling, so the transcript keeps following the run). "Continue in a new Agent chat" calls `conversation.fork` with that configuration (title "<title> (Agent)") and opens the new conversation, then starts the instruction there; if that start fails, the instruction waits in the new chat's composer. Both retry with the same command id while the request is unchanged. Files waiting in the composer stay in this conversation's composer.
  - `permissions.ts`: permission labels as the harness applies them: Supervised "Ask before commands and file changes.", Auto-accept edits "Auto-approve edits, ask before other actions.", Full access "Allow commands and edits without prompts; deleting files still asks.", and Auto (offered only to conversations already using it) "asks like Supervised". When the engine reports that commands need filesystem confinement this computer lacks (`execution.status` capabilities, read once per window by `engineCapabilities.ts`, which also serves the runtime descriptors and reads them again only when a runtime is missing from them, never on a timer; assumed on Windows until it answers), Supervised and Auto-accept edits add "Commands need Full access on this computer." The mode dialog's Permissions field uses the same descriptions.
  - `transcriptDividers.ts` (pure): `TranscriptDivider`s between root runs whose recorded mode differs ("Continued as Agent · <project> · <permission>", "Switched to Chat", "Switched to Plan · <project>", from each run's own `mode`, `workspace_id`, and `permission_mode`), at the end when the conversation was switched after its last run, and after the messages a fork copied ("Continued from <title> · Agent · <project> · <permission>"). Runs without a recorded mode (older daemons) and child runs give none. `Transcript` places them by history index and leaves out those that belong to history before the shown tail.
  - Plan cards keep Implement (switches this conversation to Agent and sends the plan) and Implement in a new chat (a new Agent chat in the same project sends the plan on arrival).
- `artifacts/`: the header's Artifacts dialog (`artifact.list`, newest first, paged) and the viewer: `Markdown` for Markdown, documents, and plans, `CodeBlock` for code and data, images (SVG included) through a `data:` URL, plain text otherwise; the first 1 MB is previewed. Download reads every `artifact.read` page (decoding base64 pages) into a `Blob` and saves it through an anchor download.

Choosing a model in an existing conversation calls `agent.configuration.set` with the full configuration and leaves the default for new chats alone. In a new chat the choice is the chat's draft and also becomes `preferences.modelId`. External runtime models switch the conversation to Agent mode with full access and need a project. Choosing a model without native tools while in Agent mode switches to Chat in the same update and says so in a toast. If a conversation was created but its first message failed, changes made since are applied before the retry.

Sending passes `skills` (the ids of `$name` mentions that name invocable skills, at most 8), in Chat with the switch on `web_search: true`, and the staged `attachments`; a retry reuses its command id only while the text, skills, switch, and attachment ids are unchanged. External runtimes get the text unchanged and no attachments.

The app root installs `useFileDropGuard` and the Tauri window sets `dragDropEnabled: false`, so HTML5 drops deliver `File` objects on Windows while a file dropped anywhere outside a drop target never navigates the window; the shell's navigation hook (`src-tauri/src/navigation.rs`) also keeps the window on the app's own pages.

`sessionConfig.test.ts` and `canResume.test.ts` run with `bun run --cwd apps/desktop test`.
